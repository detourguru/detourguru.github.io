> 브랜치 따서 코드 커밋하고 머지하는 건 똑같은데 뭐 얼마나 다르겠어?

사실 나는 svn을 써본 적이 없었지만 내가 현재 다니는 회사는 업력이 오래됐고 다른 팀에서도 대부분 svn을 사용하고 있었다. 그러다보니 신규 프로젝트를 진행하는 우리 팀도 자연스럽게 svn을 사용하게 됐다. 문제는 우리 팀의 대부분이 신입이었고, svn에 대한 이해도가 현저히 낮았다는 것이다.

아무튼 어찌저찌 svn으로 개발하던 도중 사내에서 AX와 자동화에 대한 관심이 커지면서 기존 프로젝트도 svn에서 git으로 전환하게 됐다. 프로젝트 중간에 버전 관리 시스템을 바꿔본 것은 처음 해본 경험이었다.

우리 팀이 svn을 충분히 이해하지 못해 제공되는 기능과 workflow를 적극적으로 활용하지 못했던 것도 컸지만 익숙한 git으로 전환하면서 우리가 이전에는 잘 사용하지 않았던 branch와 commit 방식을 자연스럽게 활용하게 되었고 그 결과 팀의 개발 워크플로우 자체가 바뀌었다.

## svn을 사용할 때의 워크플로우

svn에도 git의 main에 해당하는 trunk가 있고 branch도 만들 수 있다.` svn copy ^/trunk ^/branches/작업명`처럼 저장소 안의 별도 경로로 branch를 만드는 방식이다.

하지만 svn에 익숙하지 않은 팀원들이 많다 보니 작업마다 branch를 만들고 merge하는 워크플로우보다는 개인 branch를 하나 만들어 계속 사용하는 방식으로 자연스럽게 정착됐다. 

문제는 우리 프로젝트의 요구사항이 빠르게 바뀐다는 것이었다. 큰 기능을 개발하고 있는데 갑자기 우선순위가 높은 개발 요청이 들어오면 중간에 끊기도 애매하고 아직 완료되지 않은 변경사항을 가지고 있으니 새 작업을 시작하기도 부담스러웠다.

### 변경사항을 쌓아두고 한 번에 커밋하기
git이었다면 로컬에서 커밋을 만들어 작업을 쪼개고 필요하면 다른 branch로 이동해 급한 작업을 처리할 수 있었다. 반면 svn은 commit이 중앙 저장소에 바로 반영되기 때문에 git의 로컬 commit과 동일한 방식으로 체크포인트를 만드는 것은 어려웠다.

게다가 그 결과 우리 팀에서는 작업 범위가 큰 경우 변경사항을 한동안 로컬에 쌓아두다가 한 번에 commit하는 일이 잦았다.

그래서 작업 범위가 큰 경우 자연스럽게 이런 식으로 작업하게 됐다.

```text
작업 시작
  ↓
파일 계속 수정
  ↓
diff가 계속 쌓임
  ↓
한 번에 svn commit
  ↓
문제 발생
  ↓
전체 변경사항 되돌리기
```

하나의 커밋에 여러 종류의 변경이 섞이기 쉬웠고 코드리뷰를 꼼꼼히 하지 않으면 불필요한 코드가 섞이기도했다. 

## git으로 바뀌면서 달라진 워크플로우

git으로 전환한 뒤 로컬에서 작업을 안전하게 쪼갤 수 있게됐다. 브랜치를 따거나 아니면 stash를 해도 됐다.

### 작은 커밋 단위로 쪼개서 체크포인트 두기

git은 commit과 push가 분리되어 있다. 그래서 작업 중간에 로컬 커밋을 해도 다른 사람에게 바로 변경사항이 공유되는 것은 아니다. 그래서 워크플로우가 이렇게 바뀌었다.

```text
작업 시작
  ↓
작은 단위로 로컬 commit
  ↓
다음 작업
  ↓
가설 검증
  ↓
문제 있으면 이전 commit으로 돌아가기
  ↓
완료되면 push
  ↓
리뷰
```

예전에는 하나의 기능이 하나의 커밋으로 들어갔다면 git으로 바꾼 뒤에는 하나의 기능을 여러 개의 작은 커밋으로 나누는 것이 자연스러워졌다. 그래서 최신 커밋을 반영하고 에러가 나더라도 작업 전체를 원복할 필요가 없었다.

예전 로그를 보니까 에디터에 필수 validation을 붙이는 광범위한 작업을 하며 파일 114개에 6700줄이 넘는 변경사항을 한번에 커밋한 경우도 있었다. git으로 넘어온 뒤 비슷한 성격의 작업을 할일이 있었는데 정확한 비교는 할 수 없겠지만 하나의 광범위한 작업을 총 8개 커밋으로 쪼개 평균 9개 파일/200줄의 변경사항을 커밋했다.

| 구분 | 전환 이전 (커밋 2405건) | 전환 이후 (커밋 352건) |
| --- | --- | --- |
| p90 | 14개 | 10개 |
| p95 | 23개 | 15개 |
| p99 | 70개 | 23개 |

로그를 뽑아 확인해보니 git 전환 이후 커밋 단위가 많이 작아졌다는게 실제 로그에서도 확인됐다.

### 브랜치마다 AI 에이전트를 붙이기

git에서는 하나의 레파지토리에서 여러 개의 working tree를 만들 수 있다.

```
git worktree add ../worktree-api feature/api
git worktree add ../worktree-test feature/test
git worktree add ../worktree-refactor feature/refactor
```

이렇게 하면 각각의 디렉토리에서 서로 다른 브랜치를 체크아웃한 상태로 작업할 수 있다. 그럼 AI에게 하나의 브랜치를 할당한다음에 작업을 시키는 것이 가능해진다! 각 작업이 서로 다른 branch에 있기 때문에 작업 디렉토리도 분리된다.

기존에는 함수나 어떤 조각 단위로 AI에게 작업을 요청했다면 이제는 작은 기능 단위를 통째로 맡긴 다음 사람이 코드리뷰하고 머지하는 방식으로 작업 방식이 바뀌었다. 전에는 커밋 단위가 큰 경우가 잦다보니 코드리뷰가 거의 불가능했고 커밋단위의 의도 파악도 어려운 경우가 많았는데 상대적으로 코드리뷰도 많이 용이해졌다.

### 달라진 이력 조회 방법

svn을 사용할 때 AI에게 페르소나를 부여하고 QA를 시킨 파이프라인에서 에러가 발생하면 실패한 revision의 커밋 메시지를 가져오는 작업이 있었다.

svn은 저장소의 이력을 서버에서 가져오는 구조이기 때문에 커밋 메시지를 가져올때는 서버에서 로그를 조회해와야했다. 반면 git에서는 레파지토리의 이력이 로컬에 존재한다. AI QA 파이프라인에서 이력 조회가 필요한 경우에도 별도의 서버 요청 없이 로컬 레파지토리의 정보를 바로 사용할 수 있었을 뿐만 아니라 개발자가 작업하는 환경과 자동화 파이프라인이 동일한 git history를 바라볼 수 있게 됐다.

## 그렇다면 svn은 나쁜 버전관리 도구인가?

뭐가 더 나쁘고 좋고를 떠나서 두 버전관리 도구는 서로 다른 장단점이있다.

svn은 중앙 저장소를 기준으로 모든 이력이 관리되고 리비전도 순차적으로 증가하기 때문에 특정 시점의 변경사항을 추적하는 것이 직관적인 경우가 있었다. 특히 1인 개발을 진행하며 개인 branch에서 작업하고 trunk에 바로 반영하는 워크플로우에서는 git의 복잡한 branch 전략이 반드시 필요한 것도 아니었다.

반대로 팀 규모가 커서 여러 작업이 동시에 진행되거나, 요구사항이 빠르게 바뀌고 AI 에이전트까지 병렬로 작업해야하는 요구가 있는 환경에서는 git의 특성이 훨씬 잘 맞았다. 그래서 정답이 있다기보단 어떤 워크플로우를 필요로 하느냐에 따라 버전 관리 시스템의 장단점이 달라진다는 것을 알게 되었다.

## 배운 점

처음에는 svn을 사용하게 된 것을 단순히 레거시 환경에 맞추는 일이라고 생각해서 약간 불만이 있었다. 하지만 1년 반 동안 직접 사용해보니 svn에도 중앙 저장소와 선형적 커밋 히스토리처럼 분명한 장점이 있다는 것을 알게 됐다. 그리고 git으로 전환한 뒤에는 반대로 git의 장점이 단순히 많이 쓰인다는 정도가 아니라는 것도 알게 됐다. 특히 AI 에이전트를 적극적으로 활용하면서 이 차이가 더 크게 느껴졌다. 

팀이 일하는 방식과 잘 맞는 도구를 사용하는 것도 개발 환경 세팅의 중요한 한 부분이란 것을 다시 한번 되새기게 된 재밌는 경험이었다!
