최근에 대량의 데이터를 화면에 보여줘야 할 때 어떻게 처리할지, 그리고 인덱스가 잘 안 되는 DB라면 어떻게 할지를 묻는 질문을 받았다. 나는 무한 스크롤과 가상 스크롤로 답했는데, 질문의 뒷부분은 화면이 아니라 DB에서 얼마나 읽느냐에 대한 것이었다.

화면에 그리는 양과 DB에서 읽는 양이 다를 수 있다는 건 회사에서 개발 중인 서비스인 몽글의 코드에서도 그대로 보인다. 홈 목록은 화면에 카드를 20개만 그리지만 그 화면이 받는 응답에는 공개된 콘텐츠가 전부 들어 있다. 채팅은 반대로 서버에서 30개씩 나눠 받는다. 그런데 메모리에서 오래된 메시지를 잘라내면 다음에 받아올 페이지 번호가 어긋날 수 있어서 이 버그를 고친 적이 있다.

## 홈 목록은 20개만 그리지만 응답에는 전부 들어 있다

몽글 홈에는 공개된 콘텐츠가 카드로 쭉 이어진다. 처음엔 받은 목록을 `map`으로 한 번에 다 그렸는데, 4월에 홈 성능을 손보면서 이 목록에 react-virtuoso로 가상 스크롤을 넣었다. 화면 근처 카드만 DOM에 두고 멀어진 카드는 지우는 방식이다.

그런데 가상 스크롤을 넣으면서 이미지가 깜빡이는 게 보였다. 렌더할 때마다 이미지 주소 뒤에 `?t=Date.now()`가 붙어서 주소가 매번 달라지다 보니 캐시를 못 쓰고 있었다. 그래서 이 값은 같이 뺐다. 그래도 스크롤할 때 이미지를 다시 요청하는 문제는 남아서 Virtuoso를 걷어냈다. 대신 처음에 20개만 보여주고 `더보기`를 누르면 20개를 더 그리게 바꿨다.

```tsx
const { data: entireGames } = useQuery<GameListResponse>('GAMES'); // 공개 목록 전체를 한 번에 받는다
// ...
const games = filteredGames ?? []; // 장르, 검색, 정렬을 거친 목록
const paginatedGames = games.slice(0, currentPage * ITEMS_PER_PAGE); // 앞에서부터 20개, 더보기를 누르면 40개
const hasMore = paginatedGames.length < games.length; // 남았으면 더보기 버튼을 띄운다
```

처음처럼 한 번에 다 그릴 때와 비교하면 가상 스크롤이든 `더보기`든 줄어든 건 DOM에 올라가는 카드 수뿐이다. 홈 목록을 받아오는 `GET games` 요청은 두 방식 모두 파라미터 없이 한 번만 나간다. 지금 백엔드에서는 조건에 맞는 공개 콘텐츠를 전부 읽어 정렬한 다음 통째로 내려준다.

```ts
const games = await getCollection(COLLECTION_NAME)
  .find(filter, { projection })
  .toArray(); // 공개 콘텐츠를 전부 읽는다
// ...
// 접속자 수 -> 최근 7일 방문자 -> 평점 -> 리뷰 수 -> 최신 순으로 정렬해서 보낸다
formattedGames.sort((a, b) => b.onlinePlayers - a.onlinePlayers || b.recentViewers - a.recentViewers /* ... */);

res.json({ code: 200, data: formattedGames });
```

8월에 [페르소나 QA](/posts/ai-qa-trust/)를 돌릴 때 이 응답에는 공개 콘텐츠가 327건 들어 있었다. 화면에는 그중 20개만 그려진다. 그래서 게시한 콘텐츠가 목록에 있는지는 QA 스펙도 화면이 아니라 이 응답을 직접 읽어서 확인한다.

전부 받아두는 방식에도 장점은 있다. 장르나 정렬을 바꾸고 검색어를 입력해도 받은 배열 안에서 다시 거르기만 하니까 요청이 더 나가지 않는다. 그리고 정렬에 쓰는 접속자 수와 최근 7일 방문자 수는 콘텐츠 문서에 저장된 값이 아니라 백엔드가 다른 컬렉션에서 세어서 붙이는 값이다. 지금 구조에서는 공개 콘텐츠를 다 읽고 이 값을 센 다음에야 정렬할 수 있다. 그래서 응답만 20개로 잘라 보내면 응답은 작아져도 DB에서 읽는 양은 지금과 같다.

## 채팅은 위로 올릴 때마다 다음 페이지를 서버에 묻는다

홈 목록과 달리 채팅은 메시지를 처음부터 전부 받지 않는다. 플레이 화면 채팅을 위로 올려 맨 위에 닿으면 이전 메시지 30개를 더 받아와서 위에 붙인다. 화면에서 보면 무한 스크롤인데, 요청 하나하나는 몇 번째 페이지를 달라는 페이지네이션이다.

```ts
// 플레이 화면은 useChatHistory({ skipInit: true, pageSize: 30 })으로 쓴다
const nextPage = currentPageRef.current + 1; // 지금까지 받은 페이지의 다음

const data = await handleData<ChatMessagesResponse>('GET', 'CHAT_MESSAGES', {
    playDataId,
    page: nextPage,
    limit: pageSize,
});
// ...
prependChats(newMessages); // 받은 메시지를 위에 붙이고
currentPageRef.current = nextPage; // 페이지 번호를 하나 올린다
```

백엔드는 이 페이지 번호를 앞에서 건너뛸 메시지 개수로 바꾼다. 그리고 최신순으로 정렬한 메시지에서 그만큼 건너뛴 뒤 30개를 잘라서 준다. 요청마다 이 플레이어의 메시지 전체 개수도 같이 세서 전체 페이지 수를 알려준다.

```ts
const skip = (pageNum - 1) * limitNum; // 4페이지면 앞의 90개를 건너뛴다

const results = await chatHistoryCollection.aggregate([
  { $match: { receiverPlayDataId: playDataId } },
  {
    $facet: { // 개수 세기와 메시지 자르기를 한 번에 돌린다
      metadata: [{ $group: { _id: null, totalCount: { $sum: 1 } /* 안 읽은 수도 같이 센다 */ } }],
      messages: [{ $sort: { createdAt: -1 } }, { $skip: skip }, { $limit: limitNum }],
    },
  },
]).toArray();
```

받은 메시지는 Virtuoso로 그린다. 다만 [예전 글](/posts/virtuoso-chat-bottom/)에서 쓴 것처럼 바닥에서 스크롤이 흔들리지 않게, 화면 위로 미리 그려두는 범위인 `increaseViewportBy.top`을 20000px로 크게 잡아뒀다. 그래서 바닥에서는 들고 있는 메시지를 사실상 전부 그린다.

그러니까 바닥에서 DOM에 그리는 메시지 수를 제한하는 건 가상 스크롤이 아니라 메모리에 들고 있는 메시지 수의 상한이다. 바닥에 있을 때 60개를 넘으면 오래된 메시지를 잘라내고 최근 30개만 남긴다. 과거 메시지를 보는 동안에는 자르지 않는다.

## 잘라낸 만큼 다음 페이지 번호가 어긋난다

문제는 이 잘라내기와 페이지 번호가 따로 움직였다는 것이다. 최신 메시지부터 1번, 2번 순서로 번호를 매겨서 따라가보자.

처음 들어오면 1페이지로 1번부터 30번까지 받는다. 위로 올려서 2페이지와 3페이지까지 받으면 메모리에는 1번부터 90번까지 있고 페이지 번호는 3이다. 다시 바닥으로 내려오면 60개를 넘었으니 31번부터 90번까지를 잘라내고 1번부터 30번만 남긴다. 그런데 페이지 번호가 3에 그대로 있으면 다음에 위로 올렸을 때 4페이지를 요청한다. 그러면 91번부터 120번을 받아서 30번 바로 위에 붙인다. 31번부터 90번까지가 빠진 채로 이어질 수 있었던 것이다.

```text
                  메모리                 페이지 번호
3페이지까지 받음    1 ~ 90                 3
바닥에서 잘라냄     1 ~ 30                 3 (그대로)
다시 위로 올림     91 ~ 120 | 1 ~ 30      4   <- 31 ~ 90이 빠진다
```

페이지 번호는 서버가 최신 메시지부터 센 위치를 가리키는데, 잘라내기는 프론트 메모리에서만 일어났다. 메모리는 1페이지만 받은 상태로 돌아갔는데 번호는 3에 남아 있던 것이 문제였다.

그래서 메시지를 잘라낼 때 페이지 번호를 처음으로 되감으라는 신호로 `paginationResetVersion` 값을 하나 올리게 작업했다.

```ts
const trimChatStateToCap = (state: TrimmableChatState, chat: ChatHistory[] = state.chat) => {
    if (chat.length <= TRIM_TRIGGER_MESSAGES) return null; // 60개까지는 그대로 둔다

    const removedCount = chat.length - MAX_CHAT_MESSAGES;

    return {
        chat: chat.slice(removedCount), // 최근 30개만 남긴다
        paginationResetVersion: state.paginationResetVersion + 1, // 페이지 번호를 되감으라는 신호
        catchupHasMore: null,
        trimmedCount: state.trimmedCount + removedCount,
    };
};
```

채팅 히스토리를 불러오는 `useChatHistory` 훅은 이 값이 바뀌면 페이지 번호를 처음으로 되감는다. 그러면 다음 요청이 다시 1페이지부터 나가서 중간을 건너뛰지 않는다. 이렇게 다시 받은 메시지가 이미 들고 있는 메시지와 겹치면, 받은 메시지를 위에 붙이는 `prependChats`가 같은 id로 걸러낸다.

아 그리고 잘라내는 순간에 이전 메시지를 받아오는 요청이 이미 나가 있을 수도 있다. 위 예시에서 4페이지 요청이 나간 뒤 응답이 오기 전에 바닥으로 내려와 잘라냈다고 해보자. 번호를 되감아도 늦게 도착한 4페이지(91번부터 120번)가 30번 위에 붙어서 31번부터 90번까지가 똑같이 빠진다. 그래서 되감을 때 요청 버전도 하나 올리게 했다. 요청을 보낼 때 그때의 버전을 기억해두고, 응답이 왔을 때 버전이 달라져 있으면 그 응답을 버린다.

```ts
const resetPagination = useCallback(() => {
    requestVersionRef.current += 1; // 이미 나간 요청의 응답은 버리게
    // ...
    currentPageRef.current = skipInit ? 0 : 1; // 플레이 화면은 0이라 다음 요청이 1페이지
    // ...
}, [skipInit]);

// loadNextPage 안
if (requestVersion !== requestVersionRef.current) {
    return null; // 기다리는 사이에 되감겼으면 이 응답은 붙이지 않는다
}
```

잘라냈을 때만 `paginationResetVersion`이 오르는지, 요청 도중에 되감으면 늦게 온 응답을 붙이지 않는지는 테스트로 남겼다.

## 이름이 비슷해서 헷갈리는 것들

### 더보기 버튼은 서버에 아무것도 묻지 않는다

홈의 `더보기`와 채팅에서 위로 올려 더 받는 것은 둘 다 목록을 나눠서 보여준다. 그런데 `더보기`는 이미 받은 배열에서 `slice` 범위만 늘리고, 채팅은 맨 위에 닿을 때마다 `page`를 붙여 서버에 요청한다. 같은 페이지네이션이라도 홈은 브라우저에서 나누고 채팅은 서버에서 나누니까 줄어드는 것도 다르다.

| | 한 번에 받는 양 | 메모리에 들고 있는 양 | DOM에 그리는 양 |
| --- | --- | --- | --- |
| 홈 목록 | 공개 콘텐츠 전부 | 받은 것 전부 | 20개부터 `더보기`마다 20개씩 |
| 채팅 | 30개씩 | 바닥에서는 많아야 60개 | 바닥에서는 들고 있는 것 전부, 과거를 볼 때는 20000px 밖을 Virtuoso가 뺀다 |

그러니까 채팅에서 무한 스크롤은 메시지를 받아오는 방법이고 가상 스크롤은 그리는 방법이라 둘 중 하나를 고르는 관계가 아니다.

### 놓친 메시지는 페이지 번호 대신 마지막으로 받은 메시지를 기준으로 묻는다

같은 채팅인데 백그라운드에 있다가 다시 돌아와서 놓친 메시지를 받을 때는 묻는 방식이 다르다. 프론트가 마지막으로 받은 메시지 id를 소켓으로 보내면 백엔드는 그 메시지의 시각을 찾는다. 그리고 그 시각보다 뒤에 온 메시지만 가져온다.

```ts
if (sinceTimestamp) {
  query.timestamp = { $gt: sinceTimestamp }; // 마지막으로 받은 메시지보다 뒤의 것만
}

// 31개를 받아서 30개를 넘으면 더 있다고 본다. 전체 개수는 세지 않는다
const docs = await getCollection("chat_history")
  .find(query)
  .sort({ timestamp: -1, _id: -1 })
  .limit(31)
  .toArray();

const hasMore = docs.length > 30;
```

페이지 번호 방식은 "최신부터 90개 건너뛰고 30개"처럼 앞에서부터 센 위치로 묻는다. 위 채팅 쿼리에서 4페이지를 요청하면 [`$skip`](https://www.mongodb.com/docs/manual/reference/operator/aggregation/skip/)이 앞의 90개를 건너뛰는데, 건너뛸 90개도 일단 거쳐 간다. [MongoDB 문서](https://www.mongodb.com/docs/manual/reference/method/cursor.skip/)에도 `skip()`은 처음부터 훑어야 해서 건너뛰는 수가 커질수록 느려진다고 되어 있다. 거기에 이 쿼리는 요청마다 전체 개수도 센다.

놓친 메시지를 받을 때는 "이 시각 이후"라는 조건으로 묻기 때문에 앞에서 건너뛸 게 없다. 그리고 31개를 받아서 30개를 넘는지만 보면 더 있는지 알 수 있으니 전체 개수를 셀 필요도 없다. 같은 MongoDB 문서에서는 위 코드의 `$gt` 같은 범위 조건이 인덱스를 쓰면 필요 없는 문서를 훑지 않을 수 있다고 설명한다. 그래서 페이지가 깊어질수록 대체로 `skip()`보다 낫다고 한다. 다만 이 이점도 시각 조건을 인덱스로 찾을 수 있을 때 얘기다.

위로 올릴 때도 놓친 메시지를 받을 때처럼 "지금 들고 있는 가장 오래된 메시지보다 앞의 것"을 묻는다면 어떨까? 그러면 메시지를 잘라낸 뒤에도 다음 요청은 남은 메시지에서 바로 이어진다. 위 예시라면 1번부터 30번만 남은 상태에서 30번보다 오래된 31번부터 받아오게 된다. 페이지 번호를 따로 들고 있지 않으니 되감을 번호도 없다. 대신 기준 메시지 없이 몇 번째 페이지로 바로 갈 수는 없다. 그리고 운영 목록처럼 `3 / 12`를 띄우는 화면이라면 전체 개수는 여전히 따로 세야 한다.

## 배운점

그 질문에 답했던 무한 스크롤과 가상 스크롤은 몽글에서도 쓰고 있었지만 줄여주는 것은 서로 달랐다. 특히 채팅은 서버에서 나눠 받고 메모리와 DOM에서 또 따로 자르다 보니, 페이지 번호와 메모리에 남은 메시지가 서로 다른 위치를 가리키지 않게 맞춰줘야 했다.

결국 목록이 길어질 때는 기법을 고르기 전에 DB에서 읽는 양과 응답 크기, 메모리, DOM 중 무엇이 많은지 나눠 보는 게 먼저인 것 같다.
