실무에서 겪은 가상 스크롤 버그를 블로그에 정리하고 나서, 혼자 우회하고 끝내는 것보다 라이브러리 저장소에 직접 남겨서 다른 사람들의 삽질을 줄여주고 싶었다. 마침 최신 버전에서도 같은 현상이 재현되는 것을 보고 오픈소스 저장소의 문을 두드리기로 했다.

[가상 스크롤을 고치려고 가상화를 껐다](/posts/virtuoso-chat-bottom/)에서 react-virtuoso 채팅의 새 메시지가 바닥에 붙지 않고 수십 px 위에서 멈추는 현상을 다뤘다. 그때 찾은 이슈 중 [#1447 마지막 메시지를 재기 전에 바닥 위치를 계산해서 목록 중간에서 멈추는 이슈](https://github.com/petyosi/react-virtuoso/issues/1447)는 10월에도 열려 있었다. 이 이슈에는 관리자가 크기를 재려면 먼저 스크롤해야 하지 않느냐고 단 코멘트 하나만 달려 있었다.

## 최신 버전에서도 바닥에 못 붙을까?

이슈에 재현 결과를 남기려면 최신 버전에서도 같은 현상이 나는지부터 확인해야 했다. 블로그 데모는 react-virtuoso 4.18.16을 쓰고 있어서 당시 최신 버전인 4.18.19로 올리고 데모의 자동으로 보기를 다시 돌렸다. 자동으로 보기는 늦게 커지는 메시지 5개를 보내고 10개를 한꺼번에 보낸 다음 위로 올렸다가 내려오는 동작이다.

고치기 전은 바닥에 못 붙고 멈춘 게 5회였고 가만히 있는데 흔들린 거리가 307px이었다. 글에서 쓴 우회책 1번부터 3번까지를 함께 켠 고친 뒤는 둘 다 0이었다. 그러니까 9월 이후 나온 패치로도 이 현상은 그대로 남아 있었던 것이다.

## 관리자가 눌러 볼 수 있게 데모를 영어로 바꾸기

관리자가 데모를 직접 눌러 보려면 화면 문구부터 영어여야 했다. 그런데 데모의 한국어 문구는 컴포넌트마다 흩어져 있었고 블로그 영문판 글에는 데모가 아예 빠져 있었다.

그래서 문구를 `text.ts` 한 파일의 표로 모으고 데모 주소에 `?lang=en`이 붙어 있으면 영어 표를 쓰게 작업했다. 영문 글에서는 쇼트코드가 이 값을 붙여서 데모를 연다.

```ts
// 영문 글의 쇼트코드가 ?lang=en을 붙인다. 그 외에는 한국어
export const langFromQuery = (): Lang => (new URLSearchParams(window.location.search).get('lang') === 'en' ? 'en' : 'ko');
```

```ts
export const LANG: Lang = langFromQuery();
...
export const t = LANG === 'en' ? EN : KO;
```

채팅 메시지 문장도 영어로 옮겼는데 두 언어의 문장 배열 길이를 맞춰서 같은 시드면 메시지 종류와 순서가 한국어 데모와 똑같이 나온다. 다만 문장 길이가 달라서 영어 데모의 측정값은 한국어와 다르게 나올 수 있다.

## 바닥 계산 이슈에 재현 결과 남기기

바닥 계산 이슈의 [댓글](https://github.com/petyosi/react-virtuoso/issues/1447#issuecomment-6356572598)에는 4.18.19에서 재현된다는 것과 영어 데모 링크, 데모의 설정을 적었다. 설정은 `followOutput="auto"`에 `increaseViewportBy={0}`이고 이미지 칸은 300~900ms 타이머 뒤에 커지고 선택지 버튼은 500ms 뒤에 붙는다. 이미지가 커지는 건 실제 로드가 아니라 타이머라는 것도 설정에 그대로 적었다.

그리고 우회책 세 개를 함께 켰을 때 바닥 미달이 0회가 됐다는 것과 데모의 흔들림 숫자는 재마운트 때 다시 재는 다른 현상이라 이 이슈와 상관없다는 것까지 적었다. 내 경우는 스크롤이 끝난 뒤에 마지막 메시지가 또 커지는 경우라서 측정 전 크기 문제와는 조금 다른 변형일 수 있다는 것도 덧붙였다.

댓글을 올리기 전에 고친 문장 중 하나는 우회책 3번의 고정을 푸는 조건이었다. 처음엔 최근 입력이 있으면 고정을 푼다고 적었는데 코드는 300ms 안에 사용자 입력이 있었고 그 뒤에 위로 스크롤됐을 때만 고정을 푼다. 여기서 사용자 입력은 휠과 터치, 키보드와 포인터 입력이다. 그래서 두 조건을 다 적어서 올렸다.

## 트러블슈팅 문서에 빠진 경우를 PR로 올리기

바닥 계산 이슈는 라이브러리가 항목을 배치하는 구조와 엮여 있어서 코드로 고치기 어려운 문제였다. 관리자는 이 이슈에 크기를 재려면 먼저 스크롤해야 하지 않느냐고 답했다. 9월에 머지된 [#1493 prepend 보정을 같은 프레임에 적용하는 PR](https://github.com/petyosi/react-virtuoso/pull/1493)에서도 항목을 normal flow로 배치하는 지금 구조로는 새로 측정되는 항목 때문에 생기는 보정을 다 없앨 수 없다고 적었다.

반면 블로그에서 쓴 우회책 1번인 항목 높이를 마운트 시점에 확정하는 방법은 관리자가 [#1523 Message List에서 prepend 뒤 재측정으로 화면이 튀는 이슈](https://github.com/petyosi/react-virtuoso/issues/1523)에서 권한 방법과 같았다. 관리자는 그 이슈에서 이미지 같은 비동기 콘텐츠는 첫 렌더부터 크기가 정해져 있어야 한다고 답했다. 마운트 뒤에 행 크기가 바뀌면 레이아웃이 밀리고 가상화 목록은 이걸 일부만 가릴 수 있다는 것이다.

그런데 공식 [트러블슈팅 문서](https://virtuoso.dev/react-virtuoso/troubleshooting/)에는 margin 때문에 바닥까지 못 내려가는 경우와 컴포넌트를 인라인으로 정의해서 스크롤할 때마다 재마운트되는 경우는 있었지만, 화면 밖에서 돌아온 항목이 다시 마운트되면서 높이가 바뀌는 경우는 없었다. 그래서 이 경우를 설명하는 섹션을 추가하는 [#1540 재마운트 때 높이가 바뀌는 경우를 설명하는 문서 PR](https://github.com/petyosi/react-virtuoso/pull/1540)을 올렸다.

다시 마운트된 항목은 상태가 처음부터 시작되니까 높이를 바꾸는 등장 애니메이션이나 크기를 정하지 않은 이미지가 마운트될 때마다 높이를 바꾼다는 내용이다. 해결 방법으로는 이미지 칸을 미리 잡아 두고 애니메이션은 `transform`과 `opacity`만 쓰는 방법을 적었다. 그리고 한 번만 재생할 기록은 컴포넌트 밖에 id 기준으로 두게 했는데, 아래 코드에서 `playedIds`가 컴포넌트 밖에 있어서 항목이 언마운트돼도 기록이 남는다.

```jsx
const playedIds = new Set()

function Message({ message }) {
  const [animate] = React.useState(() => !playedIds.has(message.id))
  React.useEffect(() => {
    playedIds.add(message.id)
  }, [message.id])
  return <div className={animate ? 'fade-in' : undefined}>{message.text}</div>
}
```

처음 초안에는 높이가 바뀌면 스크롤 위치가 보정되면서 밀린다고 썼다. 그런데 이건 라이브러리 소스로 확인한 동작이 아니어서 관리자가 Message List 재측정 이슈에서 쓴 표현대로 레이아웃이 밀린다고만 적었다.

문서만 바꾸는 PR이라 저장소를 로컬에 받지 않고 GitHub 웹 편집기에서 fork부터 PR까지 만들었다. virtuoso 저장소는 Node 24와 pnpm 12.5 이상을 요구하는데 이 환경을 맞추는 과정을 건너뛸 수 있어서 어렵지 않았다. 처음 기여하는 사람의 PR은 관리자가 승인해야 CI가 돌아서 올린 직후에는 검사 결과가 하나도 없었다.

## PR 머지와 남은 이슈

PR을 올리고 나흘 뒤인 10월 27일, 관리자가 별도의 수정 요청 없이 PR #1540을 그대로 머지했다. 처음 올린 기여였지만 라이브러리 공식 트러블슈팅 문서에 내가 겪은 사례와 해결 코드가 반영되었다.

다만 바닥 계산 이슈 #1447은 여전히 열려 있다. 이슈에 남긴 재현 데모와 댓글에는 아직 관리자의 답이 달리지 않았다. 하지만 라이브러리 내부 배치를 뜯어고쳐야 하는 복잡한 버그와 달리, 사용자가 애플리케이션 레벨에서 피할 수 있는 트러블슈팅 가이드는 먼저 공식 문서에 올릴 수 있었다.

## 배운점

결국 이번에 virtuoso 저장소에 남긴 건 이슈 댓글 하나와 트러블슈팅 문서 32줄이었다. 몇 달 동안 이 바닥 미달 현상 하나 때문에 끙끙 앓았던 시간에 비하면 결과물 자체는 허무할 정도로 작다. (물론 그 32줄을 문서에 넣기까지 데모를 통째로 영어로 옮기고 수치를 재는 귀찮은 과정을 거치긴 했지만)

블로그에만 있던 재현 데모와 우회 방법이 이제 이슈와 문서 PR에서 링크로 이어진다.

제일 귀찮고 어려웠던 건 역시 관리자에게 내 삽질을 영어로 납득시키는 일이었다. 내 코드에선 당연하게 여겼던 타이머 동작이나 우회 조건을 관리자가 단번에 파악할 수 있게 조건 하나하나를 쪼개서 적어야 했다. 혹시 딴소리한다고 무시당하면 어쩌나 싶었는데, 다행히 데모 링크와 핵심 수치를 던져주니 의도는 통한 모양이다.

PR을 올리면서도 ‘기껏 문서 몇 줄 고치는 걸로 유난 떠는 건 아닐까’ 하는 생각이 솔직히 들었다. 코드를 뜯어고쳐서 멋지게 라이브러리 코어 버그를 해결하는 그림을 상상했었으니까. 하지만 관리자가 군말 없이 그대로 머지해 준 걸 보고 생각이 조금 바뀌었다. 라이브러리 구조상 당장 코드로 고치기 힘든 문제라면, 적어도 다음 사람이 나처럼 몇 달을 헤매지 않게 공식 문서에 지뢰밭 위치를 표시해 두는 것도 꽤 의미 있는 일이라는 걸 알았다.

처음엔 오픈소스 기여라고 하면 대단한 코드를 짜서 버그를 쾅 해결해야 하는 줄 알았다. 그런데 직접 겪어보니 그게 아니었다. ‘난 여기 알아’, ‘난 이 버그 겪어봤어’ 하면서 각자 아는 부분을 조금씩 보태 다 같이 고쳐 쓰는 쪽에 가까웠다.

방구석에서 혼자 끙끙 앓으며 삽질할 땐 막막했는데, 내가 던진 조각이 머지되는 걸 보면서 나도 개발자 커뮤니티의 일원이 된 것 같아 묘하게 감회가 새로웠다.

결국 오픈소스 기여는 거창한 문제를 해결하는 걸 넘어서, 내가 확인한 작은 조각 하나를 공유해서 다 같이 덜 삽질하게 만드는 일인 것 같다.
