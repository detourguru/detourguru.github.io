개발 후 커밋하면 QA 서버에 올라가서 QA를 받게 되는데, 이상하게 로컬에서 개발자 QA를 할 때는 안 터지던 에러들이 QA 손 한 번만 타면 바로 터지는 것 같다. 그래서 작업 -> 코드리뷰 -> 커밋의 루틴에 하나의 스텝을 더 끼워넣기로 했다. 페르소나 문서를 만들어 AI에게 부여한 다음에 Playwright MCP로 실제 서비스를 조작하면서 평가하게 했다.

우선 혼자서는 확인한 적 없었던 흐름 끊김이나 온보딩 마찰 등을 발견해내는 수확은 있었지만 문제는 속도였다. 클릭 한 번 하는데 반나절, 한 세션에 수십분. 분명히 더 빠르게 개선할 수 있는 방법이 있을 것 같았다.

## 클릭 한 번마다 비용이 든다

Playwright MCP 서버에서 액션 하나를 실행하려면 현재 화면의 접근성 스냅샷을 모델한테 보내고 -> 모델이 그걸 읽은 다음 -> 액션을 결정 -> 액션을 실행한다. 그러니까 클릭을 한 번 해도 AI에게 질문하는 비용이 든다는 말이다. 게다가 느린 건 두말할 것도 없고 말이다. 당연하겠지만 화면이 복잡할수록 더 오래 걸린다.

근데 AI가 QA하는 걸 보고 있으면 꼭 이걸 판단까지 해야 하나 싶은 구간도 있다. 예를 들면 QA를 위해 AI가 화면을 새로 띄우고 나면 서비스에 접근하기 위해 로그인을 무조건 거치게 된다. AI는 화면을 확인하고 -> 생각한다. 'button이 있네?' -> '클릭해야겠다.' -> 클릭! 하지만 이 구간은 QA 항목도 아닌 데다가 뭘 할지 이미 정해져 있는 화면이니 판단이 필요 없다. 판단이 필요 없는 스텝에까지 판단 비용을 내고 있었던 것이다.

## 실행은 코드가, 판단은 모델이

그렇다면 판단이 필요한 구간과 필요 없는 구간으로 분리하면 될 것 같았다.

1. 실행: 여정 spec, 그러니까 Playwright 테스트 코드를 작성한 다음에 전체를 한번 돌린다. 그리고 도는 동안 체크포인트마다 증거를 수집한다. 에러가 나면 무슨 에러였는지, 단계마다 얼마나 걸리는지, 화면은 어떻게 보이는지... 그리고 결과를 파일로 저장하게 했다.
2. 판단: 실행이 끝난 뒤(혹은 실패해서 중단됐을 때) 모델이 JSON을 읽고 페르소나 관점으로 분석/판단한다.

```json
{
    "step": 5,
    "name": "인물 생성 직후(목록 즉시 반영 여부)",
    "url": ".../editor",
    "visibleActions": ["'화난 고양이' 상세 열기", "'바쁜 부엉이' 상세 열기", "인물 추가", "..."],
    "durationMs": 93
}
```

이렇게 하면 각 동작마다 AI를 호출해야 했던 것에서 실행이 끝난 결과물을 1회만 읽으면 된다.

## spec을 그대로 자산으로 쌓기

근데 QA 한 번 편하게 해보겠다고 커버 안 된 쪽을 일일이 테스트 코드로 다 쓰는 건 좀 비효율적이니까 해당 기능을 QA할 때 만든 여정 spec을 쌓아서 재활용하기로 했다. 대신 AI 판정은 같은 화면에서도 실행마다 결론이 달라질 수도 있다 보니 이걸 바로 테스트 코드로 반영하진 않았다.

| | 페르소나 탐색 QA | 회귀 테스트 |
| --- | --- | --- |
| 판정 주체 | LLM | assert 코드 |
| 목적 | 새 문제 발견 | 알려진 동작 보존 |
| 실패의 의미 | 확인 필요 | 빌드하면 안 됨 |

대신 같은 조건에서 여러 번 통과했을 때만 승격하기로 결정했다. 정확히는 10번 연속 성공을 기준으로 잡았는데, 실제로 반복 호출하다 보니 부하 때문에 API 응답이 조금씩 밀리면서 걸리는 경우가 있었다. timeout을 조절하고 나서야 10번 연속 성공을 받을 수 있었다. 운 좋게 타이밍이 맞아서 통과하는 것 같은 오탐을 막으려면 이렇게 여러 번 연속 성공을 기준으로 잡아야 하는 것 같다.

또 프론트 코드만 보고 작성한 spec이 가정한 값을 화면 앵커로 썼더니 실제 백엔드에서 반환한 값과 달라서 실패하는 경우도 있었다. 처음엔 테스트가 잘못됐다고 생각했는데 실제 응답을 찍어보니 프론트가 기대하던 값이 애초에 서버가 주는 값이 아니었다. 이건 테스트를 고칠 문제가 아니라 어느 쪽 값이 맞는지부터 정해야 하는 문제였다. 이후로는 화면 앵커를 프론트 코드에서 짐작하지 않고 실제 응답을 받아서 확인한 값으로 잡았다.

백엔드 응답을 기다리지 않고 테스트 코드 여정상 다음 액션으로 넘어가서 에러 처리가 된 경우도 있었고말이다. 그래서 이런 가드 처리가 필요하다고 생각했다. 이렇게 쌓은 테스트 코드를 통해 나중에 비슷한 스코프 내에서 QA할 때 속도도 더 빠르고 안정성이 높아질 거라고 판단했다.

## 그래서 얼마나 빨라졌을까?

before는 이미 지나간 세션이라 다시 잴 수 없었는데, Claude Code 세션을 확인해서 도구 호출 횟수와 처음과 마지막 호출 시각을 뽑아보니 before는 총 22분 소요, 호출 103회 동안 조작 1회당 대략 12.8초가 소요되었다. 새로운 방식의 타임스탬프에서 확인해본 바로는 조작 1회 당 0.5초 정도로 줄었으니 조작 비용이 25배 가량 줄어든 걸 확인할 수 있었다.

// Before
스냅샷 전송 -> AI 판단 -> 클릭 실행 (12.8초) * 103회 (AI 왕복 103회)

// After
Playwright 실행 -> 체크포인트에서 증거 수집 -> evidence.json
=> LLM이 읽고 판단 (11.3초, AI 왕복 0회)

## 배운점

AI 에이전트가 고정되거나 같은 작업을 반복적으로 실행해야 하는데 그게 너무 느리다고 생각될 때, 루프 안에서 AI 판단이 필요 없는 구간을 찾아서 코드로 정해주면 더 효율적으로 AI를 활용할 수 있다는 것을 배웠다. 그리고 AI가 한 번 탐색할 때마다 spec으로 문서화하도록 해서 나중에 비슷한 동작을 할 때 재활용하게 되면, 더 적은 토큰으로 더 많은 작업을 처리할 수 있게 된다.

내가 필요했던 건 기능 QA와 페르소나 관점 분석, 두 가지였다. 기능 관련은 assert 테스트 코드로, 판단은 AI로 역할을 나눠줬더니 나름 쓸 만한 속도와 결과를 받아볼 수 있었다.
