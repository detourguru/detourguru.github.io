몽글에서 AI로 콘텐츠를 만들면 생성은 서버에서 백그라운드로 돌고, 다 끝나면 서버가 SSE로 `createComplete` 이벤트를 보내준다. 생성이 도는 동안 프로필 영역의 `내 방 꾸미기` 버튼에는 로딩 스피너가 돌고, 누르면 "아직 만들고 있어요." 토스트만 뜬다. 이 이벤트를 받아야 버튼이 풀린다.

그런데 서버는 30초 만에 생성을 끝냈는데 버튼이 새로고침하기 전까지 계속 잠겨 있는 일이 생겼다. 그 뒤에는 iOS에서 친구 요청을 받아도 알림이 안 오고 친구 목록도 갱신되지 않는 문제가 있었다. 둘 다 서버가 먼저 보내주기로 한 이벤트가 화면까지 오지 않은 경우였다.

## 기능마다 서버와 주고받는 방식이 다르다

몽글에서 서버와 데이터를 주고받는 방식은 네 가지다. 누가 먼저 보내는지와 누구와 누구 사이인지로 나눠보면 기능마다 무엇을 골랐는지가 보인다.

| 방식 | 누가 먼저 보내나 | 누구와 누구 사이 | 몽글에서 쓰는 곳 |
| --- | --- | --- | --- |
| polling | 브라우저가 정해진 간격으로 다시 묻는다 | 브라우저와 서버 | 결제 결과 확인, 관리자 서버 상태 |
| SSE | 연결을 열어두면 그 뒤로는 서버만 보낸다 | 브라우저와 서버 | 친구 요청, 생성 완료, 운영 공지, 강제 로그아웃 |
| WebSocket | 연결을 열고 나면 양쪽 다 보낸다 | 브라우저와 서버 | 게임 플레이, DM 대화방 |
| 웹훅 | 일이 생긴 서버가 상대 서버로 보낸다 | 서버와 서버 | 결제사가 결제 결과를 우리 서버로 |

게임 플레이는 플레이어가 둘러보기(`lookAround`), 전투 시작(`startBattle`), 거래 수락 같은 명령을 계속 보내고 그 결과를 같은 연결로 바로 받아야 해서 WebSocket을 쓴다. 반대로 친구 요청이나 생성 완료는 언제 생길지 서버만 알고 브라우저가 보낼 건 없다. 그래서 로그인하면 `/sse/connect`에 요청을 하나 보내고 그 HTTP 응답을 끊지 않은 채 [SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) 이벤트를 계속 받는다. (이 연결이 두 번 열리던 문제는 [예전 글](/posts/faced-three-race-conditions/)에서 다뤘다.)

polling은 바뀐 게 없어도 정해진 간격마다 요청이 나간다. 새 콘텐츠 만들기 창의 이미지 대기는 원래 1.5초마다 완료 여부를 묻는 polling이었는데, 여러 명이 동시에 이 단계를 지나면 그만큼 요청이 겹쳐 서버 부하가 된다는 지적이 나와서 SSE 구독으로 바뀌었다. 반면 관리자 서버 상태 화면은 SSE를 쓰지 않고 10초 polling으로 만들었다. 화면에 띄우는 워커 수치와 작업 큐가 서버에서 각각 10초와 15초 주기로 갱신되는 값이라 SSE로 받아도 더 빨라지지 않기 때문이다.

웹훅은 축이 다르다. 앞의 셋은 브라우저와 서버 사이의 이야기인데 웹훅은 서버가 다른 서버의 주소로 HTTP 요청을 보내는 것이라 브라우저가 끼지 않는다. 몽글에서는 결제사가 결제 결과를 우리 서버로 알려줄 때 쓰인다. CI가 실패하면 GitHub Actions가 사내 메신저의 웹훅 주소로 실패 알림을 보내는 것도 같은 방식이다.

## 웹훅은 서버가 받고 결제 결과 화면은 다시 묻는다

웹 결제는 결제창에서 결제가 끝나면 두 가지 일이 따로 일어난다. 결제사가 우리 서버로 결과를 보내고(웹훅), 결제창은 브라우저를 결제 결과 화면으로 돌려보낸다. 백엔드에서는 이 중 웹훅과 서버의 주기 작업에서만 각설탕을 지급한다. 결과 화면으로 돌아오는 건 브라우저 이동이라 중간에 빠지거나 위조될 수 있어서 화면만 넘긴다. 웹훅이 늦거나 안 오면 서버가 5분마다 대기 중인 주문의 거래 상태를 결제사에 직접 물어서 지급한다. 서버끼리도 상대가 보내주길 기다리다가 안 오면 다시 묻는 구조다.

결제 결과 화면에서는 서버에 주문 상태를 2.5초마다 다시 묻게 작업했다. 서버가 웹훅을 받자마자 지급하니까 대부분은 첫 조회에서 끝난다.

```tsx
const POLL_INTERVAL_MS = 2500;
const PENDING_TIMEOUT_MS = 60 * 1000;
...
    // 지급 여부가 아직 안 정해졌고 1분이 안 지났으면 2.5초 뒤 다시 묻는다
    refetchInterval: (query) => (!timedOut && isUnsettled(query.state.data) ? POLL_INTERVAL_MS : false),
```

React Query의 [`refetchInterval`](https://tanstack.com/query/v5/docs/framework/react/reference/useQuery)에 함수를 넘기면 쿼리 상태를 보고 다음 조회 여부를 정할 수 있다. 여기서 `isUnsettled`는 응답이 아직 없거나 요청이 실패했거나 상태가 `pending`이면 아직 모르는 것으로 보고, 완료나 실패처럼 상태가 정해지거나 서버가 거절 메시지를 줘야 끝난 것으로 본다. 그래서 요청이 한 번 실패해도 결제 실패로 띄우지 않고 2.5초 뒤에 다시 묻는다. 1분이 지나면 `timedOut`이 켜지면서 더 묻지 않고, 잠시 후 보유 각설탕을 다시 확인해 달라고 안내한다. 그 뒤의 지급은 서버의 5분 주기 작업이 맡는다.

## SSE 이벤트가 연결이 없는 프로세스로 갔다

다시 `내 방 꾸미기` 버튼으로 돌아가면, 원인은 서버 구조에 있었다. API 서버는 pm2 클러스터라서 프로세스 4개가 떠 있는데, SSE 연결 목록은 각 프로세스가 자기 메모리에만 들고 있다. 그런데 생성 완료 이벤트는 생성 작업을 처리한 프로세스가 보낸다.

예를 들어 내 SSE 연결은 1번 프로세스가 들고 있는데 생성 작업은 3번 프로세스에서 끝났다고 해보자. 3번 프로세스의 연결 목록에는 내 연결이 없으니 이벤트는 3번 프로세스의 대기 큐에 남고 나한테는 오지 않는다. 진단해보니 7번 중 4번이 이렇게 전달되지 않았다. 이벤트를 만든 프로세스와 연결을 들고 있는 프로세스가 다를 수 있다는 것이 문제였다.

<!-- 그림: 프로세스 4개 중 1번이 내 SSE 연결을 들고 있고, 생성 작업은 3번에서 끝나 완료 이벤트가 3번 대기 큐에 남는 흐름 -->

프로세스끼리 이벤트를 넘겨주는 건 백엔드에서 고쳐야 했고, 그 전까지 프론트에서는 SSE를 못 받아도 버튼이 풀리게 해야 했다. 그래서 생성 중일 때만 10초마다 사용자 정보와 내 콘텐츠 목록을 다시 받게 했다.

```ts
export const GAME_CREATION_POLL_MS = 10_000;

export const useGameCreationFallbackPoll = (isGameCreating: boolean): void => {
    const queryClient = useContext(QueryClientContext);

    useEffect(() => {
        if (!isGameCreating || !queryClient) return; // 생성 중일 때만 돈다

        const timer = setInterval(() => {
            void queryClient.invalidateQueries({ queryKey: ['CURRENT_USER'] });
            void queryClient.invalidateQueries({ queryKey: ['MY_GAMES'] });
        }, GAME_CREATION_POLL_MS);

        return () => clearInterval(timer); // 생성이 끝나 false가 되면 멈춘다
    }, [isGameCreating, queryClient]);
};
```

SSE가 제때 오면 캐시의 `createComplete`가 바로 `true`로 바뀌면서 `isGameCreating`이 `false`가 되고 polling도 같이 멈춘다. SSE를 놓쳐도 다음 조회에서 받은 목록으로 같은 일이 일어나서 늦어도 10초 남짓 뒤에는 버튼이 풀린다. 테스트로는 생성 중일 때만 10초마다 두 쿼리를 다시 받고, 생성이 끝나거나 화면을 벗어나면 멈추는지를 확인했다.

새 콘텐츠 만들기 창의 이미지 대기도 같은 이유로 늦어졌다. 앞에서 말한 대로 1.5초 polling을 SSE `stepImagesReady` 구독으로 바꾼 자리인데, 이 이벤트를 놓치면 이미지가 다 만들어졌는데도 최대 대기 시간인 60초를 다 채우고서야 다음 화면으로 넘어갔다. 여기는 SSE 구독을 그대로 두고 3초 간격 조회를 보조로 같이 돌려서 먼저 완료를 알려주는 쪽에서 넘어가게 했다. 보조 수단이라 간격은 예전에 polling만 쓸 때의 1.5초보다 느슨하게 잡았다.

```ts
export const IMAGES_POLL_MS = 3000;
...
await new Promise<void>((resolve) => {
    let settle: () => void = () => {};
    const timeoutId = setTimeout(() => settle(), IMAGES_WAIT_MAX_MS); // 60초가 지나면 그냥 넘어간다
    const unsubscribe = subscribeStepImagesReady((readyGameId) => {
        if (readyGameId !== gameId) return;
        settle(); // SSE가 먼저 오거나
    });
    const pollId = setInterval(() => {
        void stepApi.imagesStatus({ gameId }).then((res) => {
            const { payload } = readStepResult<AiStepImagesStatusResult>(res);
            if (payload?.pending === 0) settle(); // 조회에서 남은 이미지가 0개면
        });
    }, IMAGES_POLL_MS);
    let settled = false;
    settle = () => {
        if (settled) return; // 셋 중 먼저 온 것만 처리한다
        settled = true;
        clearTimeout(timeoutId);
        clearInterval(pollId);
        unsubscribe();
        resolve();
    };
});
```

SSE와 조회 응답, 타임아웃이 거의 동시에 올 수 있어서 `settled`로 한 번만 정리한다. 테스트로는 SSE가 안 와도 조회가 `pending: 0`을 돌려주면 60초를 기다리지 않고 넘어가는지, 아직 남은 이미지가 있으면 계속 기다리는지를 확인했다.

이후 백엔드에서 근본 수정이 들어갔다. 이벤트를 보낼 때 자기 프로세스의 연결에 바로 쓰는 것과 별개로 DB의 `sse_events` 컬렉션에도 적고, 프로세스마다 1초 주기로 이 컬렉션을 읽어서 자기 연결에 전달하는 방식이다. 브라우저에 SSE를 제대로 보내려고 서버 안에서는 polling을 하게 된 셈이다.

## 끊긴 SSE 연결이 살아 있는 것처럼 남았다

iOS에서 친구 요청 알림이 안 오던 문제는 원인이 달랐다. iOS는 앱이 백그라운드에 있는 동안 웹뷰의 네트워크를 멈추는데, 이렇게 끊긴 SSE 연결은 에러도 종료도 없이 멈춘 채로 남는다. `onclose`나 `onerror`가 오지 않으니 기존 재연결 로직이 돌 기회가 없었던 것이다. 게다가 친구 요청과 수락 이벤트는 그 순간 붙어 있는 연결에만 보내고 큐에 남기지 않아서 나중에 다시 연결돼도 놓친 이벤트는 다시 오지 않는다.

그래서 백엔드 SSE 라우트에 주석 처리돼 있던 heartbeat를 살려서 서버가 25초마다 `ping` 이벤트를 보내게 했다. 클라이언트는 ping이 오기 시작한 연결에서 60초 동안(ping 두 번) 아무것도 못 받으면 그 연결을 버리고 새로 연다. 앱에 돌아왔을 때도 마지막으로 받은 지 30초가 넘었으면 바로 새로 연다. 마지막 ping을 받고 20초 만에 돌아오면 연결을 그대로 두고 2분 뒤에 돌아오면 바로 새로 연결하는 식이다. 이렇게 새로 연 연결에서는 친구 목록과 생성 상태를 다시 받아서 끊겨 있던 동안 놓친 이벤트를 메운다. 토스트는 놓쳐도 목록은 맞출 수 있다.

게임 플레이 WebSocket은 이보다 먼저 같은 문제를 겪었는데, 이쪽은 앱에 돌아오면 `ping`을 보내고 3초 안에 `pong`이 없으면 화면을 새로고침하게 해뒀다.

## SSE 이벤트마다 놓쳤을 때 메우는 방법이 다르다

운영 공지는 접속 중인 사람에게만 오고 못 받은 사람은 알림함과 배지로 보게 되어 있어서 따로 메우지 않는다. 친구 요청은 다시 연결될 때 목록만 다시 받는다. polling까지 같이 돌리는 건 생성 완료나 이미지 완료, 운영자 화면의 전체 공지 발송 완료처럼 놓치면 화면이 진행 중 상태에서 멈춰 버리는 이벤트다.

이런 polling은 전부 그 상태인 동안만 돌고 상태가 바뀌면 멈춘다. 공지 발송도 보내는 중인 공지가 있는 동안만 3초마다 목록을 다시 부른다. DM 목록은 조건이 조금 다른데, 앱 전역 SSE가 연결돼 있으면 polling을 끄고 끊겨 있을 때만 5초마다 다시 묻는다.

## 배운점

몽글에서 실시간 연결이 놓친 걸 메운 방법을 모아보면 전부 다시 묻는 쪽이었다. 브라우저는 서버에, 서버는 결제사와 DB에 다시 묻는다. 결국 SSE나 웹훅은 빨리 알려주는 역할이고, 끝났는지를 확정하는 건 다시 묻는 쪽이 맡아야 하는 것 같다.
