출근길에 SNS에서 어떤 게임회사의 기획자가 개발자가 하는 말은 하나도 알아들을 수 없다는 내용의 콘텐츠를 봤다. 일단 그 영상의 내용은 이랬다. NPC 대화를 배열로 저장해둔 서비스에 "대화 중간에 분기를 넣어달라"는 요구가 들어왔다. 개발자는 기획자에게 "배열을 그래프로 바꿔야 하는데 그럼 구조랑 파서를 다 갈아엎어야 해서 부담"이라고 했다. 그러다가 갑자기 "아! 저장은 배열로 두고 추상 구조만 그래프로 얹으면 되겠네요?"라고 말하며 작업을 하러갔다는 내용이었다. 그 영상의 댓글로는 포인터 주소 계산, general tree, 메모리 낭비 같은 단어들이 오갔다.

근데 이 영상 속 개발자의 말을 나도 반도 이해 못 했다. 그래서 위기감을 느끼고 용어를 하나씩 공부하다보니 다름아닌 내가 개발중인 게임 플랫폼의 이벤트 시스템이 정확히 이 개발자의 셀프 논쟁의 결론 지점에 있었고 동일한 결론을 냈던 것이다. 사람은 역시 배워야한다더니... 이제부터 내가 이 대화에서 언급된, 모르던 용어들을 하나씩 분해해보며 내가 이름 붙이지 못했던 개념에 라벨링을 해보려한다.

## "배열을 그래프로 바꿔야 하는데"

### 배열 구조

우리 모두가 알다시피 배열 저장 구조의 전제는 다음 항목은 항상 index + 1이라는 것이다.

```ts
const dialogue = [
  { speaker: "npc", text: "어서 오게." }, // 0
  { speaker: "npc", text: "부탁이 하나 있네." }, // 0 + 1
  { speaker: "player", text: "무슨 부탁인데요?" }, // 1 + 1
];
```

이런 대화 배열 데이터가 있다고 가정할때 이 대화를 진행하는 방법은 순회를 돌며 하나씩 꺼내가는 것이다. 0, 1, 2 순이다.
진행도 저장도 index 값 하나로 관리가 가능하다. 하지만 분기가 생긴다면? 그러니까 0 다음에 1 뿐만 아니라 2도 올 수 있어야한다면?

### 중첩 구조

가장 직관적으로 생각했을 때에는 데이터가 분기에 따라 반환해야할 값을 직접 가지고 있는 트리 구조가 정답일 것처럼 보였다.

```ts
const dialogue = {
    text: '부탁이 하나 있네.',
    choices: [
        { label: '물론 들어드리죠.', next: { text: '고맙네!', choices: [...] } },
        { label: '무시한다', next: { text: '아쉽군...', choices: [...] } },
    ],
};
```

실제로도 갈라지기만 하는 대화라면 이걸로 충분하다. 하지만 게임을 좀 해봤다면 알겠지만 많은 퀘스트는 합류 구조를 가지게된다. 그러니까 수락하든 거절하든 같은 이벤트로 모이는 흐름말이다.

```text
수락 ──> 고맙네! ──┐
                   ├──> 다음에 또 보세
거절 ──> 아쉽군... ┘
```

만약 중첩구조를 사용하는데 이런 합류 대사를 던져야한다면 이 합류대사를 모든 선택지마다 넣어주어야하고 복사가 되어버린 이상 여러군데에서 관리를 해주어야하는 불편함이 있다. 한군데에서 관리를 하게 된다면 이미 지나간 진행 흐름을 앞 노드로 다시 가져와야하는데 중첩 구조에서는 이렇게 순환 참조 구조로 사용하기가 어렵다. 객체가 자기 조상을 자식으로 품는 꼴이다.

## "그럼 구조랑 파서를 다 갈아엎어야 해서 부담"

그러니까 "배열을 그래프로 바꿔야 하는데 그럼 구조랑 파서를 다 갈아엎어야 해서 부담"라는 말의 정체는 배열에서 '그래프'로 데이터 구조를 바꿔줘야하는데 그러면 기존의 선형적으로 진행하던 구조에서 참조형으로 구조를 변경하고 그에 맞추어 진행 파서도 다 갈아야한다는 뜻이었던 것이다.

## 그럼 그래프는 어떻게 생긴걸까?

자 그럼 앞의 중첩 구조가 못 하던 합류와 순환까지 표현할 수 있는 그래프는 어떻게 생긴걸까? 크게 세가지 방식으로 그래프를 표현할 수 있다.

### 위치 공식으로 계산

첫번째 방법은 연결 정보를 별도로 가지고 있지는 않되 공식으로 위치를 계산하는 방식이다. 그러니까 예를들어 2번째 노드가 0: 예, 1: 아니오, 2: 점프하기. 와 같은 데이터를 가지고있다면 그냥 2번쨰 대화를 찾고 해당 노드의 자식을 공식으로 찾아오면 된다. 데이터를 별도로 가지고있지 않아도되니 깔끔해보이지만, 이 공식이 성립하기 위해서는 실제로 데이터가 있든 말든간에 모든 노드가 같은 수의 자식만큼의 칸을 예약해야한다. 최대 선택지가 4개라면 선택지가 1개뿐인 대사도 배열에서 4칸을 차지한다는 뜻이다.

depth가 깊어질수록 당연히 낭비가 지수적으로 커진다. 대화 깊이 5라면 슬롯이 4⁵ = 1,024개 필요한데, 실제 대사가 30개면 994칸이 빈 채로 할당될 것이다. 선형적으로 진행되다가 가끔 가다가 분기가 있는 대화 케이스에는 최악이라고 할 수 있다.

### 인접 리스트 방식

노드들은 순서 상관없이 flat하게 배열에 담아두고 대신 각각 다음 선택지 배열을 들고있는 방식이다.

```ts
const nodes = [
  { id: "greet", text: "부탁이 하나 있네.", next: ["accept", "refuse"] },
  { id: "accept", text: "고맙네!", next: ["bye"] },
  { id: "refuse", text: "아쉽군...", next: ["bye"] },
  { id: "bye", text: "다음에 또 보세.", next: [] },
];
```

같은 id를 가지면 합류, 앞 노드의 id를 가지고있으면 순환이 된다. 우리 서비스에서는 캐릭터 생성 중 confirm 스텝에서 (정말 생성하시겠습니까? 예, 아니오...) 사용되었다.

### 읽기 비용 줄이는 팁

`events.find(e => e.id === id)`를 하면 배열을 앞에서부터 쭉 훑게 되는데 이벤트가 1,000개면 조회 한 번에 평균 500번 비교이고 렌더링마다 반복하면 부담이 된다. `new Map(events.map(e => [e.id, e]))`로 인덱스를 한 번 만들어두면 이후 조회는 `map.get(id)`로 줄어든다.

### 간선 리스트 방식

마지막으로는 연결을 별도의 목록으로 저장하는 간선 리스트 방식이다. 인접 리스트는 노드가 다음 선택지를 직접 들고 있는 방식이었다. 간선 리스트는 이 연결 정보를 노드 밖으로 완전히 꺼내서 별도로 관리한다.

```ts
const edges = [
  { from: "greet", to: "accept", label: "수락한다", condition: "level >= 5" },
  { from: "greet", to: "refuse", label: "거절한다" },
  { from: "accept", to: "bye" },
  { from: "refuse", to: "bye" },
];
```

node.next를 읽는 게 훨씬 쉬워 보이는데 왜 이렇게 간접적으로 다음 노드를 불러와야 할까? 그 이유는 메타데이터를 가질 수 있는 상황 때문이다. 예를 들어 위 예제의 accept/refuse 두 간선은 같은 greet에서 출발하지만 label이 다르고, accept 쪽에만 level 조건을 붙일 수도 있다. 그러니까 인접 리스트는 다음이 누구인지 알면 되는 단순한 분기에 적합하지만 간선 리스트는 조건이나 그 분기만의 데이터를 가져야 할 때 적합하다.

우리 서비스에서 플레이어에게 보여지는 선택지 데이터가 정확히 이 케이스다. 에디터 특성 상 같은 다음 이벤트로 가더라도 선택지 문구가 상황마다 다르게 배치할 수 있도록 연결 자체에 라벨을 붙일 수 있는 간선 리스트 구조를 쓴다.

## "저장은 배열로 두고 추상 구조만 그래프로"

보다시피 세 가지 방식의 공통점은 물리적 저장은 여전히 배열에 한다는 점이다. 그러니 저장은 배열에 두고, 추상 구조만 그래프로 -> 라는 뜻은 연결관계를 표현하는 논리 구조를 그래프로만 변경하고 저장은 그대로 배열에 한다는 말이었다.

### 트리에 참조가 있으면 그게 곧 그래프 아닌가?

처음엔 이 부분이 조금 헷갈렸는데 모든 트리는 그래프고, 각 그래프를 구현하는 방식이 다른 것 뿐이다. 위치 공식은 규칙적인 트리 모양만 표현할 수 있고, 참조 저장은 합류/순환을 포함한 임의의 그래프를 표현할 수 있다.

## 내 프로젝트에서 확인한 것

용어를 공부하고 나서 내 이벤트 시스템 코드를 다시 열어봤다. 위에서 다룬 선택지 데이터와 달리 이벤트끼리 연결되는 부분(연계 이벤트)과 캐릭터 생성 스텝은 애초에 "이벤트는 상하위 개념 없이 같은 뎁스에서 서로를 참조할 수 있어야 한다"는 요구만 가지고 구조를 이렇게 잡았었다.

```ts
type EditorData = {
  events: Array<{ id: string; trigger: string; basicScript: Script[] }>;
};

interface LinkedEvents {
  type: "random" | "priority" | "choices"; // 다음 이벤트 선정 방식
  data: Array<{ eventId: string }>; // 연결은 id 참조로
}
```

그러니까 내가 사용하는 방식은 인접, 간선 리스트 방식의 혼합이었던 것이다. 사실 복잡한 데이터 안에 또 다른 데이터가 있는게 너무 무거울 것 같아 id를 두고 평탄화해서 서로를 참조하게 설계한건데 적절한 방식이었던 것 같다.

다만 단점으로는 중첩 구조는 부모를 지우면 자식이 같이 사라지지만 참조 구조에서 노드를 지우려면 그 노드를 가리키던 참조를 전부 찾아서 같이 지워야 한다는 단점이 있다. 아니면 고아 객체가 남게될 수도 있어서 참조 노드까지 정리해주는게 좋다.
