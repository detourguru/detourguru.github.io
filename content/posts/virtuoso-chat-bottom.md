웹에서 실시간 멀티 채팅을 구현해야 한다는 얘기를 들었을 때 내 머릿속에 가장 먼저 떠오른 건 성능 문제였다. 최적화와 긴 싸움을 하게 되겠다는 예상이 들었다. 게다가 우리 서비스는 애니메이션 연출도 있고 채팅마다 길이도 출력되는 타이밍도 다르니 이 모든 걸 조율하는 것도 일이었다. (스크롤도 평범하지 않다. 조건이 두 개 이상 달린 스마트 스크롤에 자동 스크롤, 수동 스크롤까지 전부 지원해야 했다)

이런 이유로 가상 스크롤을 도입하던 2025년 8월 경에 먼저 붙여 본 건 인지도가 높은 TanStack의 react-virtual이었다. 그런데 이미 짜 둔 자동 스크롤 로직이 가상 목록 위에서는 먹히지 않았다. 바닥 따라가기를 TanStack 위에서 새로 짜느니 최근 100개만 잘라서 그리는 게 빨랐고 그렇게 직접 윈도잉으로 넘어갔다. FE 신입인 나한테는 너무 어려운 과제였고 유지보수도 쉽지 않았다.

결정적으로 자동 스크롤이 계속 깨졌다. 절망에 빠져 `virtual list auto scroll bottom` 이런 식으로 검색을 하다보니 react-virtuoso 공식 문서를 보게 됐는데 아예 채팅 유즈케이스를 내세우고 있었다. 확인해보니 `followOutput`, `firstItemIndex`, `startReached`처럼 필요한 게 다 들어있어서, 2026년 2월 경 스크롤 로직을 통째로 이 라이브러리로 넘길 수 있었다.

그런데 새로운 문제가 발생했다. 새 메시지가 왔는데 바닥에 메시지가 붙지 않고 수십 px 위에서 멈추는 현상이 생겼다. 그리고 바닥에 가만히 있는데도 메시지가 올 때마다 스크롤이 위아래로 흔들린다.

## 현상 A. 스크롤이 새 메시지를 따라가지 못한다
 
바닥에 있을 때 새 메시지를 따라가는 `followOutput`, 또는 마지막 메시지로 이동하는 `scrollToIndex({ index: 'LAST', align: 'end' })`를 쓰면 virtuoso는 스크롤 목표 위치를 대략 이렇게 계산한다.
 
```text
targetScrollTop =
  lastItemTop        // 마지막 메시지가 시작하는 위치
  + lastItemHeight   // 마지막 메시지 높이 (추정 값)
  - viewportHeight   // 화면 높이
```
 
그러니까 마지막 메시지가 5000px에서 시작하고 화면 높이가 800px라고 하자. item의 높이를 아직 재본 적이 없다면 virtuoso는 실제 높이를 알 수가 없다. 그래서 첫 item에서 얻은 높이나 `defaultItemHeight`로 대신 계산한다. 그렇게 얻은 추정 높이가 80px이라면 목표는 4280px이 된다 (5000 + 80 - 800 = 4280).
 
그런데 실제 높이가 추정 높이보다 크다면? 예를 들어 240px이라고 친다면 진짜 바닥은 4440px이 된다 (5000 + 240 - 800 = 4440). 스크롤은 160px 모자란 곳에서 멈추게 된다.
 
virtuoso에도 재시도 로직이 있어서 대부분은 측정이 끝난 뒤 보정된다. 근데 스크롤이 끝난 다음에 item의 높이가 커졌다면? 예를 들어 뒤늦게 로드된 이미지라든가, 애니메이션이 아이템의 높이를 바꾼다든가, 버튼이나 선택지가 렌더 후에 붙는다든가, 텍스트가 계속 늘어난다든가... (맞다, 모두 우리 서비스에서 등장한 현상들이다.)
 
이런 item들은 아무래도 스크롤 시점과 크기 확정 시점의 순서가 매번 달라질 수밖에 없다. 타이밍이 잘 맞아 크기가 먼저 확정되었다면 정상적으로 스크롤이 따라붙겠지만 스크롤이 먼저 끝나면 늘어난 만큼 바닥에서 떨어진 채 멈춘다.
 
나만 이런 증상을 겪는 줄 알았더니 유사한 증상들이 virtuoso github에 이슈로도 올라와 있었다. [#1273](https://github.com/petyosi/react-virtuoso/issues/1273)은 메시지를 빠르게 연속 추가하면 마지막 항목 중간에서 멈춘다는 보고다 (관리자는 margin이 문제일거라고 추측했다). 

특히 [#1447](https://github.com/petyosi/react-virtuoso/issues/1447)은 아까의 계산식이 측정 전 기본값을 쓴다는 걸 짚고있는데 관리자가 크기를 재려면 일단 스크롤을 해야 하지 않느냐고 코멘트를 달아놨다. 사실 나도 딱 여기에서 막혀버리긴했다. `정확히 스크롤하려면 -> 크기를 알아야 하고 -> 크기를 알려면 -> 먼저 그려야 하는데 -> 그리고 난 후에 -> 크기가 변한다`. 1447 이슈는 글을 쓰는 26년 9월 시점까지 open 되어 있는 진행중인 이슈다.

## 현상 B. 메시지가 쌓이면 스크롤이 튀고, 지나간 애니메이션이 다시 재생된다

virtuoso는 화면에 보여지는 것보다 조금 넓은 범위까지 미리 그려둔다 (overscan). 그리고 overscan 밖으로 나간 item은 DOM에서 지운다. 이때 지우면서 높이는 기억해두는데 전체 목록 높이를 알아야 스크롤바 길이를 맞출 수 있기 때문이다. 그러다 나갔던 item이 다시 화면에 들어오면 새 DOM 노드로 다시 그려진다. 그러면 다시 관찰 대상이 되고 그 과정에서 크기를 새로 측정하게 된다.

문제는 이때 잰 높이가 기억해둔 높이와 다를 수 있다는 것이다 (화면 너비가 바뀌었거나 재마운트 과정에서 상태가 초기화되어 요소의 크기가 달라졌을 수 있으니까). 그러면 목록 전체 높이가 그 차이만큼 바뀌고 스크롤 위치도 따라서 보정된다. 그러니 가만히 있는 화면이 위아래로 흔들리는 것처럼 보인다.

followOutput 옵션을 켜둔 상태라면 증상이 하나 더 추가된다. 측정이 흔들리는 동안 바닥에 있는지 아닌지 판정이 틀려서 엉뚱한 위치로 스크롤해버리면서 스크롤 점프가 발생한다.

virtuoso는 ResizeObserver로 각 element의 크기를 재고 있으므로 새 DOM 노드로 잡히는 item의 재측정을 피하려면 아예 지우지 않거나, 다시 쟀을 때 같은 값이 나오게 해야 한다.

## 관리자가 답변한 해결방법

### margin이 있진 않나요?
virtuoso 공식 트러블슈팅 문서에서 이러한 현상에 대해 가장 첫번째로 드는 원인은 다름아닌 margin이다. 아까 말한 것처럼 virtuoso는 `ResizeObserver`로 item 높이를 재는데 이렇게 잰 높이에는 margin이 포함되지 않기 때문이다. 그래서 item에 margin이 있으면 그만큼이 측정에서 통째로 빠지고 전체 높이가 실제보다 작게 계산돼 바닥까지 스크롤이 안 될 수 있으므로 padding으로 여백을 표시하는 것이 좋다.

### Virtuoso message list를 사용해보세요

이슈 트래커들을 살펴보면 이런 유사 증상은 꽤 많은 사용자들이 겪고 있는 것으로 보인다. 또 이슈 번호만 봐도 알겠지만 매우 유서깊은 (?) 이슈다. ([#127](https://github.com/petyosi/react-virtuoso/issues/127), [#199](https://github.com/petyosi/react-virtuoso/issues/199), [#1273](https://github.com/petyosi/react-virtuoso/issues/1273), [#1447](https://github.com/petyosi/react-virtuoso/issues/1447)). 

이 이슈들에 대한 관리자의 입장은 꽤 일관적인데 이런 문제들에 대해 적극적으로 리뷰하고 머지하고 있지만 한편으로는 채팅 스크롤을 완전히 안정시키는 건 현재 구조로는 한계가 있고 그 [한계를 없애려면 배치 방식 자체를 바꿔야 한다](https://github.com/petyosi/react-virtuoso/pull/1493)고 직접 말하기도 했다.

그러면서 채팅에는 [Virtuoso Message List](https://virtuoso.dev/message-list)를 권장한다고 답변하고 있다. 과거 기록을 불러온 뒤 위로 스크롤하는 테스트에서 일반 virtuoso는 약 85px, Message List는 1px 미만 움직였다고 한다. 내가 겪은 현상 `B`에는 확실히 효과가 있을 것 같긴하지만 상용 라이선스라 유료다. 또 이미지나 영상 크기를 미리 지정해서 렌더 후 크기가 바뀌지 않게 하라고 답변하기도 했다 ([#1083](https://github.com/petyosi/react-virtuoso/discussions/1083)).

결국 item이 순차적으로 쌓이는 normal flow로 배치되는 구조의 라이브러리와 item 별 가변 높이 + 렌더 후 크기 변화 + 바닥 고정이라는 요구사항이 만난 결과가 바로 위의 두 현상인 셈이다.

## 내가 우회해서 해결해본 방법들

비용이 적은 순으로 적어보았다. 물론 마법처럼 하나로 딱 해결된건 아니고 다 섞어서 사용했다.

### 1. 항목 높이를 마운트 시점에 확정하기
 
첫 번째 방법은 이 현상이 발생하는 원인을 없애는 것이다. 이미지는 `width/height`나 `aspect-ratio`로 자리를 미리 잡아 두면 로드 전후 높이가 같아진다. 관리자가 권하는 방법이기도 하다 (렌더 이후 높이 변경이 일어나지 않도록 함).
 
가상화는 화면 밖 메시지를 지웠다가 다시 그리는데 이때 컴포넌트 상태가 사라져서 지나간 메시지의 등장 애니메이션이 처음부터 다시 재생된다. 그래서 재생 여부를 메시지 id 기준으로 기록해 두고 처음 등장할 때만 재생하게 했다. 혹시 높이를 바꾸는 연출이 섞일 수도 있으니 애니메이션은 높이를 건드리지 않도록 `transform`과 `opacity`만 쓰게 했다.

여기서 포인트는 애니메이션 재생 기록을 컴포넌트 밖에 둬야 한다는 것이다. 안에 두면 컴포넌트가 언마운트될 때 같이 사라져서 아무 소용이 없다.
 
```tsx
const playedEntryIds = new Set<string>()
 
function MessageRow({ message }: { message: Message }) {
  const [animate] = useState(() => !playedEntryIds.has(message.id))
  useEffect(() => {
    playedEntryIds.add(message.id)
  }, [message.id])
  return <div className={animate ? 'animate-fade-in' : undefined}>{/* ... */}</div>
}
```

다만 이 방법은 서버가 이미지 크기를 내려줘야 쓸 수 있고, AI 응답처럼 토큰 단위로 오는 메시지는 높이를 미리 알 수가 없어서 전부 적용하지는 못했다.

### 2. 스크롤 바닥 근처를 언마운트 대상에서 빼기

`B` 현상의 주요 원인은 바닥 근처의 item이 언마운트와 마운트를 오가며 상태가 초기화되어 item의 높이가 변할 수 있었던 것이었다 (1번에서 말한대로 가상화가 다시 그리기 때문이다). 그럼 바닥 근처는 아예 언마운트 안되게 하면 어떨까? `increaseViewportBy.top`을 크게 잡고 목록 길이에 상한을 두었다.

```tsx
const MAX_MESSAGES = 60 // 목록 상한
const MAX_ROW_HEIGHT = 200 // item 중 가장 큰 추정 높이

// 항상 MAX_MESSAGES * MAX_ROW_HEIGHT < increaseViewportBy.top 이 되도록 top을 아주 크게 잡는다
<Virtuoso increaseViewportBy={{ top: 20000, bottom: 1200 }} /* ... */ />
```

`MAX_MESSAGES * MAX_ROW_HEIGHT < increaseViewportBy.top`, 그러니까 총 item들의 높이가 increaseViewportBy.top보다 작으면 스크롤이 바닥에 있을 때 목록 전체가 항상 렌더 영역 안에 들어가게된다.

픽셀 방식은 보다시피 `MAX_ROW_HEIGHT`의 추정치가 실제 item 최대 높이와 얼마나 근사하느냐가 매우 중요하다. 만약 `increaseViewportBy.top` 값을 넘는다면 다시 스크롤이 바닥에 안붙는 이슈가 발생할 것이다. 실제로도 이 값을 3000px로 잡았을 때는 메시지가 쌓이고 나니 중간에 스크롤이 멈추고 튀는 현상이 다시 돌아왔다.

이 방식을 쓰면 사용할때 주의할점은, 바닥 근처에서는 가상화가 사실상 꺼지게 된다는 것이다. 가상화로 성능을 최적화하는 것이 아니라 목록 상한이 성능을 좌우하게 되는데 virtuoso의 측정 비용은 여전히 발생한다. 우리 서비스처럼 과거 히스토리 무한 스크롤까지 보장해주어야한다면 보이는 화면 내에서의 상한을 언제 적용할지도 같이 설계해줘야한다. 과거 기록을 보는 중에는 자르기를 미루고 바닥으로 돌아오면 자르는 식으로 말이다.

#### minOverscanItemCount 옵션
픽셀 대신 MAX_MESSAGES 개수로 잡는 방법도 있다. `minOverscanItemCount` 옵션을 사용하는 것인데  [릴리즈노트](https://virtuoso.dev/react-virtuoso/changelog/)에서도 `increaseViewportBy`로 잡을 수 없는 큰 항목이거나 접기/펴기가 가능한 item 용이라고 되어 있다.
 
```tsx
<Virtuoso minOverscanItemCount={{ top: MAX_MESSAGES, bottom: 0 }} /* ... */ />
```
 
이쪽은 `MAX_ROW_HEIGHT` 추정이 아예 필요 없다. 그래서 이게 나의 `B`현상을 해결해 줄 것 처럼 보였다. 그런데 재현해보니 재마운트되며 튀는 현상은 막았지만 메시지를 추가할 때 scrollHeight가 최대 110px 가까이 줄었다 늘어나는 출렁임이 남았다. 게다가 처음 불러온 목록에 렌더 후 커지는 메시지가 섞여 있으면, 5번 중 3번은 재마운트가 천 번 넘게 반복되면서 바닥에서 5000px 넘게 떨어지기도했다. 원인까지는 확인하지 못했지만 바로 갈아탈 수 있는 옵션은 아닌 것 같아서 도입하지 않았다.

### 3. followOutput 대신 직접 바닥에 붙이기

`followOutput`은 스크롤이 바닥에 있을 때 새 메시지를 따라가게 하는 옵션이다. 그런데 얘가 먼저 계산을 끝내고 바닥으로 스크롤을 붙였는데 갑자기 item의 높이가 달라지면 스크롤이 바닥에서 떨어지게 된다. 하지만 그 시점에는 이미 바닥이 아니므로 스크롤이 다시 따라 붙지 않아 스크롤이 바닥에 붙지 않는 현상이 생기게 된다. 그래서 우리 서비스에선 `followOutput`을 끄고 같은 동작을 직접 구현했다. 

```ts
let pinned = startsAtBottom // 안읽은 메시지처럼 중간에서 시작하는 화면이면 false

// 스크롤 고정은 사용자가 직접 위로 올렸을 때만 푼다
scroller.addEventListener('scroll', () => {
  const atBottom = distanceToBottom() <= 1
  const userScrolledUp = scrolledUp() && !contentShrank()

  if (atBottom) pinned = true
  // 바닥 거리를 기준으로 false로 풀어줬더니 빠르게 추가되는 상황에서는 
  // 바닥이 아닌것으로 오판하는 경우가 있어서 위로 올렸을때를 기준으로 풀어준다
  else if (userScrolledUp) pinned = false 
})

// 채팅 목록 크기가 바뀌면 스크롤이 고정 상태일 때만 바닥으로 보낸다
new ResizeObserver(() => {
  if (pinned) scroller.scrollTop = scroller.scrollHeight
}).observe(list)
```

`followOutput`이 하던 동작을 직접 구현한거면 뭐가 차이일지 헷갈릴 수 있는데 포인트는 판단 조건이다. 

| | 언제 | 조건 | 어디로 |
|---|---|---|---|
| `followOutput` | 메시지가 추가될 때 | 지금 바닥에 있으면 | 계산한 위치로 |
| 직접 구현 | 목록 크기가 바뀔 때 | 사용자가 바닥을 떠나지 않았으면 | 실제 끝으로 |

처음엔 메시지가 오면 일정 시간 동안 계속 바닥으로 끌어내리는 방식을 써보기도 했는데 virtuoso의 재측정과 싸우면서 오히려 스크롤 떨림이 더욱 심해졌다. 크기가 바뀔 때만 반응하게 바꾸고 나서야 안정됐다.

재현해보니 천천히 추가할때는 전부 바닥에 잘 붙었지만 빠르게 추가하면 여전히 스크롤이 바닥에 안붙는 현상이 있었다. 그래서 단독으로 사용할 순 없었지만 바로 위의 2번과 같이 사용했을 때 효과가 좋았다.

### 4. 보이는 부분은 비가상, 안보이는 부분은 가상으로 처리하기

사실 이 방법이 가장 깔끔하긴 하다. 최근 item들은 일반 DOM으로 그려서 브라우저가 레이아웃과 바닥 고정을 직접 처리하게 하고, 화면 밖의 과거 기록만 가상화하는 방법이다. 

실제로 이 방법을 도입하기 위해 테스트를 몇차례 진행하기도 했다. 비가상화 목록에서 스크롤 바닥고정은 ResizeObserver로 콘텐츠 높이 변화를 감지해서 바닥 근처면 따라붙는 방식으로 처리할 수 있었다. 그런데 문제는 남은 작업들이었다. 비가상 -> 가상으로 item이 넘어갈때, 화면 전환시 스크롤 정렬, 과거 기록 무한 스크롤 등등... 그냥 채팅 목록을 아예 새로 구현하는 수준의 범위였다. 

이 화면은 우리 서비스에서 가장 중요한 화면이고, 거의 모든 로직이 이 스크롤에 달려있었기 때문에 작업 범위를 정하는 것부터가 사실 좀 부담이었다. 게다가 이것저것 시도해보며 바닥에 도달하지 못하는 현상은 위의 2+3번으로 이미 상당 부분 잡을 수 있었고, 남은 증상에 비해 ROI가 작다고 생각해서 실제 도입을 하진 않았다. 하지만 나중에 이 부분을 아예 리팩토링 해야한다면 4번으로 바로 도입할 것 같다.

## 대체 방법: TanStack Virtual로 갈아타기

처음에 TanStack Virtual을 도입했다가 바로 걷어낸건 채팅 기능이 없어서였다. 바닥 따라가기나 과거 기록을 prepend할 때 위치 보정 등의 로직을 전부 tanstack 위에서 새로 짜야했는데 그럴바엔 그냥 100개만 잘라서 윈도잉으로 직접 작업하는게 훨씬 빠르다고 판단했다.

그런데 이 아티클을 쓰기위해 찾아보니 2026년 5월에 TanStack Virtual에 `anchorTo: 'end'`가 추가되었다고 한다. virtuoso의 followOutput과 비슷한 옵션인 것 같긴한데 바닥 정렬을 측정된 높이의 합이 아니라 DOM의 실제 최대 스크롤값으로 계산하고, 스크롤이 바닥에 붙어 있는 동안 목록 높이가 커지면 그만큼 따라 내려간다. `A` 현상에서 문제였던 '스크롤을 내려야 높이를 재는데 높이가 계속 변한다'를 아예 우회하는 접근이다. 내가 3번에서 직접 짠 로직을 라이브러리가 맡아주는 셈이기도 하다. 항목을 absolute로 배치하니까 normal flow 밀림도 없을거고 prepend 위치 유지도 메시지 key 기준으로 해준다.

가볍게 재현해보니 `A`는 어떤 조건에서도 안나왔지만 `B`는 다시 그릴 때 높이가 달라지는 메시지가 섞여있으면 여전히 스크롤 튐 현상이 있었다. 그러니 만약 tanstack을 도입한다면 1번 (높이 사전 확정) 작업은 별도로 필요할 것 같다.

아까도 말했듯이 채팅 화면은 우리 서비스의 가장 중요한 화면인데다가 별의별 기능이 다 붙어있어서 채팅 컴포넌트는 1500줄에 달하고 있다 (리팩토링을 한번 거쳤는데도 이모양이다). 그래서 교체 비용도 있고 e2e도 virtuoso에 묶여있다. 솔직히 tanstack으로 갈아탄다고 모든 문제가 해결된다면 비용을 들여서라도 교체를 감수할만하겠지만 아직 신규 기능이다보니 좀 더 두고봐야할 것 같다.

게다가 tanstack virtual의 이슈 트래커를 보면 이 라이브러리 역시도 내가 여름 내내 겪은 것과 같은 계열의 버그를 여전히 고치고 있다. 전체 높이가 반영되기 전에 `scrollTop`을 써서 브라우저가 값을 잘라버리는 문제, 스트리밍 메시지가 커지면서 화면이 밀리는 문제, prepend 후 위쪽에 빈틈이 생기는 문제 같은 것들이다.

### 비교 표

| 방법 | A (바닥 미달) | B (흔들림) | 비용/한계 |
|---|---|---|---|
| 1. 높이 사전 확정 | 완화 | 완화 | 콘텐츠 제약. 스트리밍엔 한계 |
| 2. 바닥 근처 언마운트 방지 | - | 해결 | 바닥 근처 가상화 이득 없음 / 행 높이 가정 필요 |
| 3. 크기 변화 시 다시 붙이기 | 단독 불가 | - | 직접 짜는 코드 |
| 2 + 3 | 해결 | 해결 | 한계도 2+3 |
| 4. 바닥만 비가상 | 해결 | 해결 | 경계 처리 리팩토링 |
| 5. Message List | 확인필요 | 해결 | 상용 라이선스 |
| 6. TanStack 전환 | 해결 | 일부해결 | 헤드리스라서 UI 직접 구성 / 신규 기능이라 도입 리스크있음 |

item의 높이를 통제할 수 있다면 1번이 정답일 수 있다. margin 제거나 애니메이션 중복 재생 방지만으로도 증상이 꽤 줄어들 수 있다. 높이를 지정할 수 없다면 2+3의 조합을 사용하면 된다.

과거 히스토리가 길거나 원활한 스크롤 품질이 중요하다면 코드 비용이냐 라이센스 비용이냐를 따져서 4번이나 5번 중 하나를 도입해보면 좋을 것 같다.

마지막으로는 새로 가상화 라이브러리를 도입하려고 고려중이라면 [virtuoso와 tanstack을 비교](https://npmtrends.com/@tanstack/react-virtual-vs-react-virtuoso-vs-react-window) 해보면 도움이 될 것 같다.

## 배운점

지금 우리 서비스에선 1+2+3번으로 굴러가고있다. 등장 애니메이션은 메시지 id 기준으로 한 번만 재생하고, `followOutput`은 꺼뒀고 item의 크기가 변하면 바닥에 직접 붙인다. `increaseViewportBy.top`을 아주 크게 잡아서 바닥 근처의 가상화를 사실상 꺼 뒀다. 가상 스크롤을 고치려고 가상화를 끈 셈이다.

2025년 8월 어설프게 도입했던 tanstack으로 시작해 직접 윈도잉을 거쳐 2026년 2월 virtuoso를 도입하기까지 반 년이 걸렸고 그 뒤 virtuoso가 풀지 못한 문제를 붙잡고 다시 반년 가까이를 보냈다. (물론 중간에 다른 급건 일감들이 들어와서 계속 손대지 못하긴했지만) 기능이 너무 많이 달린 화면이라 싹 갈아엎기엔 걸린 코드가 많았고 구조를 갈아 엎는다고 회귀가 없으리란 보장도 없어서 더 어려웠다. 게다가 요구사항이 계속 바뀌고 추가되는 환경에서 최적화와 버그 개선까지 진행하는 것이 결코 쉽지는 않았다.

처음부터 virtuoso를 골랐다면 시행착오를 좀 줄일 수 있었을까? 지금 생각해보면 아닐 것 같다. normal flow로 배치하는 라이브러리를 골랐다면 어느 쪽이든 결국 같은 벽을 만났을 테니까. 아쉬운 건 라이브러리를 고를 때 기능 목록만 봤다는 점이다. `followOutput`이 있다는 것과 내 화면이 원하는 방식으로 바닥에 붙는다는 건 다른 얘기였다는 것을 당시에는 알지 못했다. 다음에 가상화를 도입하게 된다면 어떤 옵션이 있는지보다 item을 어떻게 배치하는지를 먼저 볼 것 같다.
