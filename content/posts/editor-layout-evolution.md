회사에서 개발 중인 서비스인 몽글에 처음 들어갔을 때 들은 건 노코드 게임 에디터를 만든다는 얘기뿐이었다. 그런데 막상 만들어 보니 노코드라는 말과 달리 에디터가 다뤄야 하는 데이터는 거의 코드만큼 복잡했다. 항목 하나가 다른 항목이나 에셋을 여러 개 참조하는 식이었다.

그래서 1년 반 동안 에디터 화면의 틀이 두 번 바뀌었다. 처음엔 단계를 따라가는 화면이었고, 그 다음엔 메뉴로 화면을 고르는 구조, 지금은 여러 패널을 한 화면에 띄우는 구조다. 모바일용 틀은 그 사이에 따로 하나 만들었다.

## 첫 번째: 상관없는 데이터도 단계를 따라 넘겨야 했다

2025년 3월의 첫 화면은 단계별 진행이었다. 위쪽에 진행 막대와 이전, 다음 버튼이 있고 가운데 카드에 지금 단계의 화면이 들어간다. 단계 순서는 정해져 있어서 세 번째 단계를 보려면 다음을 두 번 눌러야 했다.

그런데 에셋 중에는 다른 에셋과 상관없이 혼자 설정하면 되는 것도 있었다. 그런 에셋 하나를 고치려 해도 앞 단계부터 순서대로 넘겨야 하니 불편했다. 단계라는 틀이 데이터 사이에 없는 순서를 강제하는 것이 문제였다.

그래서 3주 뒤에 진행 막대를 없애고 메뉴에서 화면을 바로 고르게 바꿨다. 아래 코드는 패널로 바꾸기 직전인 2025년 9월의 레이아웃이다.

```tsx
<FormProvider {...methods}>
    <div className="bg-basic mx-auto flex size-full gap-5 p-6">
        <SideNav /> {/* 고른 묶음 안의 화면 목록 */}
        <div className="flex flex-1 flex-col gap-5">
            <div className="bg-sub flex h-20 min-h-20 justify-between rounded-2xl p-6">
                <Title>{currentName}</Title>
                ...
            </div>
            <main className="bg-sub flex size-full gap-5 overflow-y-auto rounded-2xl p-6 shadow-md">
                <Outlet /> {/* 지금 주소에 맞는 화면 하나 */}
            </main>
        </div>
    </div>
</FormProvider>
```

화면은 `<Outlet />` 한 곳에 들어간다. 메뉴를 누르면 주소가 바뀐다. 그러면 그 주소에 연결된 페이지 컴포넌트가 들어오고 이전 페이지는 언마운트된다. 그러니까 이 구조에서는 주소 하나가 곧 화면 하나였다. 위쪽 제목바의 저장 버튼이 페이지 안의 폼을 저장하는 방식은 [폼은 누가 가지고 있어야 할까?](/posts/form-ownership-in-react/)에서 다뤘다.

## 두 번째: 서로 참조하는 데이터를 한 번에 하나씩만 볼 수 있었다

메뉴 구조는 독립된 에셋을 고르기엔 편했지만, 서로 참조하는 데이터를 고칠 때 막혔다. 항목 하나를 고치려면 그 항목에 놓을 에셋과 이어진 다른 항목을 같이 봐야 하는데, 화면은 여전히 하나씩만 보였다. 실제 화면도 데모의 메뉴와 카드 탭처럼 항목 화면을 보다가 캔버스를 누르면 카드가 통째로 캔버스로 바뀌었다. 노코드지만 코드만큼 얽힌 데이터를 다루려면 여러 요소를 한 번에 볼 수 있는 화면이 필요했다.

그래서 2025년 10월에 화면을 여러 패널로 나눴다. 왼쪽에는 메뉴, 오른쪽에는 속성 패널을 두고 가운데는 위아래로 나눠 캔버스와 에셋 목록을 넣었다. 이 넷이 한 화면에 같이 떠 있다. 패널 크기 조절은 [react-resizable-panels](https://github.com/bvaughn/react-resizable-panels)에 맡겼다.

```tsx
<PanelGroup direction="horizontal" className="h-full">
    <ActivityBar />
    <NavigationPanel activeItem={currentPath} gameName={gameData?.name ?? ''} />
    ...
    <Panel defaultSize={50} minSize={0}>
        <PanelGroup direction="vertical">
            <Panel defaultSize={70} minSize={30}>
                ...
                <CreateMap /> {/* 캔버스 */}
            </Panel>
            ...
            <Panel defaultSize={30} minSize={15} maxSize={50}>
                <PanelGroup direction="horizontal">
                    <Panel defaultSize={20} minSize={20} maxSize={50}>
                        <DatabasePanel /> {/* 에셋 종류 */}
                    </Panel>
                    ...
                    <Panel defaultSize={80} minSize={40}>
                        <AssetsPanel activeItem={currentPath} revealKey={locationKey} /> {/* 에셋 목록 */}
                    </Panel>
                </PanelGroup>
            </Panel>
        </PanelGroup>
    </Panel>
    ...
    <Panel defaultSize={30} minSize={0} maxSize={40}>
        <InspectorPanel key={pathname} ... /> {/* 속성 패널. 주소가 바뀌면 이것만 다시 마운트된다 */}
    </Panel>
</PanelGroup>
```

가로 그룹 안에 세로 그룹을, 세로 그룹 안에 다시 가로 그룹을 넣어서 캔버스 아래에 에셋 목록이 오게 했다. `defaultSize`와 `minSize`는 그룹 크기에 대한 퍼센트라서 화면 너비가 달라져도 비율이 유지된다. 패널 사이를 드래그해 크기를 바꾸는 계산은 라이브러리가 한다.

주소는 이 구조에서도 쓴다. 다만 주소가 정하는 범위가 화면 전체에서 속성 패널 하나로 줄었다. 라우트 화면은 속성 패널 안의 `<Outlet />`에 들어온다. 속성 패널에는 `key={pathname}`을 줘서 주소가 바뀌면 속성 패널만 새로 마운트된다. 캔버스와 에셋 목록은 레이아웃에 있으니 주소가 바뀌어도 그대로 남는다. 예를 들어 캔버스에서 항목 1 카드를 누르면 항목 1의 상세 주소로 이동한다. 이때 다시 마운트되는 건 오른쪽 속성 패널뿐이고 캔버스는 그대로다.

대신 주소 하나만 보고는 지금 화면을 다 알 수 없게 됐다. 속성 패널은 주소가 정하지만 캔버스에 어느 그룹을 띄울지는 스토어 값(`selectedAreaInfo`)이 정하기 때문이다. 그래서 지금 화면 상태를 확인하려면 주소와 스토어를 같이 봐야 한다.

## 세 번째: 패널을 여러 개 띄운 화면은 폰에서 너무 복잡했다

모바일에서도 에디터를 쓸 수 있게 하려다 보니 패널 구조는 좁은 화면에 넣기엔 너무 복잡했다. 그래서 2026년 1월에 모바일 에디터를 간단한 버전으로 따로 만들었다.

모바일 에디터는 새 틀을 짜는 대신 플레이 화면에 쓰는 컴포넌트를 그대로 가져왔다.

```tsx
<GamePlayLayout className="bg-stage">
    <div ref={headerRef} className="bg-m-ink sticky top-0 z-20 shrink-0">
        <GamePlayHeader gameMode="editor" ... /> {/* 플레이 화면 헤더를 편집 모드로 */}
    </div>
    <main ...>
        {mode === 'preview' ? <EditorMudPreview /> : <FormRenderer ... />}
    </main>
    <GamePlayBackground backgroundImage={...} />
</GamePlayLayout>
...
<MudGestureArea directions={swipeDirections} onMove={handleSwipeMove} ... /> {/* 플레이 화면과 같은 스와이프로 옆 항목 편집으로 이동 */}
```

헤더와 레이아웃, 배경은 플레이 화면과 같은 컴포넌트고, 가운데에만 편집용 폼(`FormRenderer`)이 들어간다. 옆 항목으로 넘어가는 것도 플레이 화면의 스와이프를 그대로 쓴다. 그래서 사용자는 플레이어가 보게 될 화면과 같은 모양 위에서 바로 고치게 된다.

고칠 항목을 고르는 방식도 PC와 다르다. PC는 항목마다 상세 주소가 있어서 그 주소에 따라 속성 패널의 `<Outlet />`이 바뀐다. 모바일은 한 페이지 안에서 주소의 쿼리(`?location=`)로 고칠 항목만 바꾼다.

## 배운점

단계별 진행은 3주, 메뉴와 카드는 6개월 남짓 썼고, 패널 구조는 2025년 10월부터 지금까지 쓰고 있다. 화면 틀을 바꿀 때마다 기준이 된 건 데이터가 서로 얼마나 얽혀 있는지였고, 한 번에 같이 봐야 하는 것이 늘어날수록 한 화면에 띄우는 영역도 늘었다. 모바일은 그 영역을 줄이는 대신 아예 다른 틀을 골랐다.

결국 에디터 화면의 틀은 다루는 데이터의 모양을 따라가는 것 같다.
