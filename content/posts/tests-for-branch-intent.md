기능 하나를 고쳤는데 전혀 상관없어 보이던 다른 화면이 깨진 경험은 아마 개발자라면 한번쯤은 겪어봤을 것 같다. 게다가 혼자 개발하면 그걸 알려줄 사람도 없어서 대개 사용자가 먼저 발견하기도 한다.

내가 개발한 회전문이 딱 이런 케이스였다. 캐스팅보드 이미지를 올리면 AI가 읽어서 날짜별 출연 배우를 정리해주는데, AI가 읽어온 결과를 믿을 수 없으니 코드에서 한 번 더 걸러낸다. 오류 제보가 들어올 때마다 조건이 늘어서 이 검증 로직이 파일 하나에 880줄 가까이 커져버렸다.

그런데 테스트코드가 없다보니 분기를 더할 때마다 기존 분기의 의도가 살아 있는지 확인할 방법이 수기로 직접 기능을 테스트해보는 방법밖엔 없었다. 가장 큰 문제는 수기 테스트 범위가 넓어서 한 번 고친 버그가 다른 수정 때문에 되살아나도 알 수가 없었다는 것이다.

## 테스트코드를 붙인 기준

테스트코드가 필요했던 이유는 명확했다.

- 한 번 고친 버그가 다시 생겼다.
- AI 파싱 결과를 거르는 규칙이 계속 커지기만하고 검증은 안됐다.
- 1인 개발이다보니 내 수정이 맞는지 확인해줄 사람이 없었다. 문제를 사용자 버그 제보로 알게 되는 경우도 있었다.

코드 베이스가 좀 많다보니 어떤 시나리오를 붙여야할지, 어디서부터 시작해야할지 난감했다.
그래서 우선 범위는 순수 함수로 좁히고 기준을 두 개로 잡았다. 순수 함수의 모든 분기에 테스트를 붙이고, 발생했던 버그마다 그 버그를 재현하는 테스트를 붙인다.

### 모든 분기에 한 케이스씩

예를들면 AI가 읽은 날짜 배지(프리뷰, 막공 같은 표시)를 거르는 함수는 이런 조건식으로 되어 있다.

```ts
const isValid =
  tag.length > 0 && // 배지 이름이 있나?
  DATE_PATTERN.test(startDate) && // 날짜 형식이 맞나?
  startDate <= endDate && // 시작일이 종료일보다 늦지는 않은가?
  startDate >= from && // 공연 기간 안인가?
  endDate <= to &&
  agreesWithPrintedWeekday(startDate, printedStartWeekday) && // 적힌 요일이 실제 날짜와 맞나?
  ... // 회차 시간, 이미지 업로드 인덱스 검사 등 11개 조건
```

이 조건 하나하나가 곧 AI가 틀릴 수 있는 경우의 수 하나를 의미한다. 이 중 하나라도 틀리면 건너뛴다. 그런데 문제는 너무 조건이 많다보니 이 중에 하나가 틀릴때 무엇이 왜 틀리는지 바로 알기가 어렵다는 거였다. 만약 코드 수정 중 조건 하나가 빠진다면? 그래도 알아차리기 어려울 수 있다.

그래서 이러한 분기를 검증하는 테스트코드를 아래처럼 작성했다.

```ts
it.each<[string, ParsedDateTag]>([
  ["배지 이름이 비어 있으면", dateTag(" ", "2026-09-28", "2026-09-28")],
  ["시작일이 종료일보다 늦으면", dateTag("프리뷰", "2026-09-29", "2026-09-28")],
  ["적힌 요일이 실제 요일과 다르면", dateTag("프리뷰", "2026-09-28", "2026-09-28", { printedStartWeekday: "화" })],
  ["회차 배지가 하루가 아니라 기간에 걸쳐 있으면", dateTag("막공", "2026-09-28", "2026-09-29", { time: "19:30" })],
  ...
])("%s 버린다", (_, invalid) => {
  expect(normalize([invalid])).toStrictEqual([]);
});
```

일단 테스트코드를 작성하고 나서는 꼭 원본코드를 망가뜨려보고 테스트코드가 실패하는지도 직접 확인했다. 그러지 않으면 어떤 경우에도 통과하는 쓸데없는 테스트코드를 생성할 수 있기 때문이다.

버리면 안 되는 경우도 똑같이 테스트로 고정했다. `소속사 공지 이벤트는 적힌 요일이 날짜와 안 맞아도 버리지 않는다`와 같은 조건이었다. 소속사 SNS에 올라오는 이벤트는 오탈자일 수 있어서 버리는 대신 업로더에게 확인을 요청한다.

```ts
it("요일이 날짜와 맞지 않아도 오탈자일 수 있어 버리지 않는다 (확인 화면에서 확인을 요청한다)", ...);
```

### 과거 버그마다 회귀 테스트

두 번째 기준은 한 번 발생했던 버그에 대한 테스트코드였다. fix 프리픽스가 붙은 커밋 메시지를 쭉 확인해서 그 버그가 다시 생길 때 실패하는 테스트를 붙였다. 예를 들면 KOPIS API가 정상 요청에도 가끔 400을 줘서 재시도와 동시 요청 제한을 넣었던 적이 있는데, 여기에는 이런 테스트가 붙었다.

```ts
it("KOPIS가 간헐적으로 400을 주면 다시 요청해서 결과를 받는다", ...);
it("동시에 많이 조회해도 KOPIS에는 8개까지만 한꺼번에 요청한다", ...);
```

1000행이 넘는 조회를 나눠 읽는 로직이나 캘린더 이벤트 제목이 겹치지 않게 줄을 나누는 로직도 같은 방식으로 붙였다.

## 테스트를 쓰다가 새로 찾은 버그도 있었다

캐스팅 목록 끝의 "정휘 등"에서 "등"을 떼는 함수의 정규식이 `/등$/`라서 이름 자체가 "등"으로 끝나는 배우는 마지막 글자가 잘리고 있었다. 예를들어 배우 이름이 `신호등` 이라면 `신호`만 남을 수도 있었던 것이다. 그래서 "등" 앞에 공백이 있을 때만 떼도록 정규식을 `/ 등$/`로 고쳤다. 테스트코드를 작성해보지 않았다면 등으로 끝나는 배우가 나타날때까지 알 수 없었던 류의 버그였다.

버그인지 기획인지 애매한 것들도 있었다. 내 일정에서 시간이 겹치는 공연을 표시하는데, 앞 공연이 끝나는 시각에 딱 맞춰 시작하는 공연은 겹치지 않는다고 나왔다. 그러니까 12시~13시 공연과 13시~14시 공연은 계산으로는 겹치지 않는 것이 맞지만 현실적으로 13시에 끝나는 공연을 보고 13시에 시작하는 공연을 보러 갈 수는 없다. 그래서 겹치는 공연으로 치는 것이 서비스 관점에서 합리적이라는 판단이 들어 이것도 수정했다.

## 잘 쓰인 테스트 시나리오가 곧 의사결정기록이다

테스트를 쓰려면 아무래도 그 분기가 왜 있는지 뭘하는지 알아야 한다. 그런데 이유가 코드 어디에도 없는 분기도 가끔 있었다. 이건 새로 읽은 이벤트가 이미 저장된 이벤트와 동일한지 중복을 판단하는 함수다.

```ts
export const isExactSameEvent = (event, candidate) =>
  !candidate.edited &&
  event.periodStart === candidate.periodStart &&
  // ...
```

그런데 왜 누가 한번 정정한 이벤트는 내용이 동일해도 중복 이벤트로 안친다는걸까? 너무 오래전에 작업해서 이 분기의 존재 이유가 기억이 잘 안났다. 커밋 이력을 뒤져봤지만 배역 순서를 고치는 관계없는 커밋에 섞여 들어와 있었고 설명도 없었다.

그래서 호출부를 따라가 봤다. 새로 읽은 이벤트가 기존 이벤트와 같다고 판단되면 올린 사람에게 묻지 않고 기존 이벤트에 합치는데, 화면에는 나중에 들어온 이벤트가 보이게된다 (최신 버전이니까). 그런데 이 함수는 제목과 기간만 비교한다. 그러니까 누가 설명을 직접 고쳐둔 이벤트가 있어도 같은 공지를 AI가 또 다시 읽으면 제목과 기간이 같으니 그대로 합쳐져버려서 사용자가 고쳐둔 설명이 AI가 읽은 설명으로 바뀌어버릴 수 있다. 그래서 이 조건은 사람이 고친 이벤트가 AI가 다시 읽은 내용과 자동으로 합쳐지지 않게 막는 분기였다.

이유를 찾아내고 나서 분기에도 주석을 달았고 테스트 제목에도 구체적으로 적었다. 나중에 누가 이 조건을 지우려고 하면 테스트가 제목으로 이유를 알려줄 것이다.

```ts
it("정정된 이벤트는 최신 버전이 정정 내용을 가리지 않도록 자동으로 합칠 대상에서 뺀다", () => {
  expect(isExactSameEvent(pending, existing({ edited: true }))).toBe(false);
});
```

## 배운점

처음부터 테스트코드를 썼어야했는데 빠르게 MVP를 구현하려고 하다가 `아 이 기능만 붙이고 해야지`를 반복하다보니 테스트코드가 너무 늦게 붙은 것 같다. 직접 작성한 코드인데도 불과 몇 주 지났다고 왜 있는 분기인지 헷갈리기도하고 그새 데드코드가 생기기도 하고...

그렇게 순수 함수부터 빡세게 작업을 했다. 처음 작성해보는 테스트코드 패턴은 학습 해가면서 직접 작성했고, 비슷한 형태의 테스트코드는 시나리오만 내가 확정하고 AI에게 작업을 부탁했다. 일부러 틀려보고 불필요한 테스트인지도 검수했다. 결과적으로 test 커밋이 60개 넘게 쌓였고 테스트는 500여 개가 됐다.

아직 컴포넌트 테스트랑 DB 테스트라는 큰 산이 남아있어서 커버리지는 낮지만 최소한 순수 함수는 대부분 커버되었다.

| 범위 | 분기 커버리지 |
|---|---|
| `src` | 18.7% |
| AI 결과 검증과 정리 (`normalize.ts`) | 89.5% |
| 공연 목록 필터와 정렬 (`show.ts`) | 89.7% |
| KOPIS 조회와 재시도 (`kopis.ts`) | 95.7% |

몰아서 테스트코드를 쓰다보니 너무 힘들었고 특히 이유를 모르겠을때 더 어려웠다. 테스트코드는 기능이 추가될때마다 작성해야한다는 것을 뼈저리게 느꼈다. 앞으로는 판단해서 결정한 내용이나 버그가 발생했던 내용을 그때그때 테스트코드로 남겨서 빚덩어리가 되지 않게 하려고 한다. 같은 실수를 반복하지 않기위해 CI에도 지금보다 조금 낮은 커버리지 하한선을 걸어둬서 테스트코드없는 코드가 늘어나지 않게 방지처리를 해두었다.

사실 버그 회귀를 막으려고 테스트를 붙이게 된건데 테스트코드를 쓰다보니 테스트 제목을 의사결정 기록처럼 더 자세히 쓰는 것에 신경을 많이 쓰게됐다. 앞으로는 판단해서 결정한 내용이나 버그가 발생했던 내용을 그때그때 테스트 제목에 이유까지 적어서 남기려고 한다.
