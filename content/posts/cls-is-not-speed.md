웹서비스 성능 개선을 하려고 하면 보통 라이트하우스부터 돌리게된다. 점수가 나오고, 빨갛게 뜨면 이제 그걸 하나씩 없애야한다. 그런데 지표가 좋아지는 것과 실제로 빠르게 느껴지는 건 좀 다른 얘기인 것 같다. 실제로 78%나 개선했는데도 느리다는 리포트를 받은 경험이 있다.

## CLS는 "예약 안 된 공간"의 지표다

플랫폼 메인은 가장 많이 접근하게 될 화면인만큼 빠릿빠릿해야하는데 콜드 로드 CLS가 0.385였다. 보통 Good 기준이 0.1 미만이니까 무려 4배 가까이 느린 셈이었다. 원인 파악을 위해 화면을 보니 첫 페인트에서 게임 목록이 화면 위쪽에 그려졌다가 사용자 데이터가 도착하는 순간 프로필 블록에 데이터가 채워지며 늘어나서 목록 전체가 아래로 밀리고 있었다.

```tsx
// 조건부 렌더가 공간을 예약하지 않음
{user && <PlatformUserInfo user={user} />}   // user 도착 전엔 프로필 섹션을 표시하지 않음
<GamesWithFilter />                           // 그래서 목록이 위에서 시작했다가 밀림

// 높이가 부모에 의존
<Avatar className="h-full" />   // flex 부모 높이가 확정되기 전까지 0
```

'데이터 없을때 그리지 않음'과 '높이가 부모에 의존하는 h-full'은 흔한 패턴인데 브라우저 관점에선 이 둘이 이 자리에 뭐가 올지 미리 알려주지 않는 마크업이기 때문에 문제가 된 것이다.

> 레이아웃 시프트가 생기는 매커니즘은 단순하다. 브라우저는 매 렌더마다 현재 가진 정보로 레이아웃을 확정하고 페인트한다. 데이터, 이미지 등이 나중에 도착해서 이미 그려진 요소 위쪽의 크기를 바꾸면 아래 요소들의 시작좌표는 전부 이동한다. CLS는 그 이동량과 영향 면적의 누적이다. 그래서 CLS를 개선하려면 미리 알려주기만 해도 된다.

```tsx
// 데이터가 없어도 공간을 예약
{
  user ? (
    <PlatformUserInfo user={user} />
  ) : (
    <div className="min-h-80">
      <Loading />
    </div>
  );
}

// 높이를 부모 의존에서 고정값으로
<Avatar className="h-30" />;
```

임의의 높이로 예약을 해주었기 때문에 실제 콘텐츠 높이와 정확히 일치하지 않아 작은 shift가 남긴하지만 Good 기준인 0.1 미만을 충족해서 목표를 만족했다고 판단하고 여기까지 작업했다.

원래 0.4 가까이였던걸 0.1로 바꿔놨으니 유의미하게 빨라졌겠지? 하지만 CLS를 78%나 개선하고 모든 지표가 Good으로 바뀌었는데도 서비스가 '빠릿빠릿'하지 않다는 리포트는 계속되었다. 특히 첫 방문때 많이 느리다고 했다.

## 지표를 줄인다고 빨라지는건 아니었다

그 이유는 CLS가 속도 지표가 아니기 때문이었다. 그냥 단순히 보이는 라이트하우스 숫자를 줄인다고 속도가 빨라지는게 아니었다. 속도 지표는 다름 아닌 가장 큰 콘텐츠가 언제 보이는가를 판단하는 LCP였다. CLS는 오히려 스켈레톤 UI같은걸 붙여서 안정적으로 느릴 수 있게 도와주는 지표였다.

초기 로딩을 조금이라도 줄여볼까 싶어 함께 진행한 코드 스플리팅 작업의 After를 재려고 랜딩 첫 로드의 네트워크 캡처를 떴다. JS는 스플리팅 전 1032KB에서 35% 감소된 초기 로드 674KB로 많이 줄였다. 그런데 캡처해놓고 보니 첫 로드 시 대략 4MB 정도가 되는 온보딩 안내 이미지 PNG들이 요청되고있었다. 열심히 JS 번들을 줄여놨더니 캐로셀 UI에서 아직 도달하지도 않은 온보딩 섹션을 위한 이미지들이 첫 화면 로드에 실려오고 있었던 것이다.

그러니 지표에도 안잡힐만했다. 이미지 자리는 예약되어있었으니 CLS는 0이었을 것이고 첫 뷰포트의 최대요소도 아니었으므로 LCP에도 영향이 안갔다. JS가 아니니 번들 분석에도 없었다. 모든 지표는 Good이었지만 첫 방문 시마다 4MB가 전송되고있었다. 그러니 이상하게 첫 방문시에만 느리다는 리포트가 왔던 것이다.

이후 이미지도 webp 확장자로 변경하고 lazy 로딩도 적용해주었다. 그리고 네트워크 실측 결과 3.7MB -> 466KB까지 용량을 87% 줄일 수 있었다. (뜻하지 않게 APK 빌드 시 에셋 용량도 줄였다)

```tsx
<img
  src={`/image/${img}`} // webp 확장자로 변경
  alt={img}
  loading={index === 0 ? "eager" : "lazy"} // 0번째 사진은 먼저 나오도록하고 뒤 인덱스들은 lazy 로딩
  fetchPriority={index === 0 ? "high" : undefined}
  decoding="async"
/>
```

## 배운점

CLS는 안정성, LCP는 속도, 번들 크기는 JS 용량만 잰다. 지표를 고치기 전에 그 지표가 뭘 처리하는지 부터 확인했어야했다. 그리고 라이트하우스 지표가 다 초록색이라고 안심하지 말고 느린 현상이 있을때는 전송량 목록을 같이 확인해봐야한다는 것도 알게되었다.
