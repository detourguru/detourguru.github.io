우리 팀은 프론트엔드 1명, 백엔드 1명, PL 1명이 전부다. QA 담당자가 따로 없다 보니 회귀 확인은 배포 직전에 직접 한 번 훑어보는 게 전부였다. 그래서 [지난 글](/posts/mcp-qa-too-slow/)에서 페르소나 QA를 Playwright 스펙으로 돌리고, AI는 실행이 끝난 뒤 증거 JSON만 읽고 판정하게 바꿔서 QA 속도를 올리기도 했다.

그런데 빨리 돌린다고 바로 팀에서 쓸 수 있는 건 아니었다. AI가 발견이라고 올린 항목을 화면에서 직접 확인해보면 멀쩡한 경우가 많았고, 그러면 내가 AI 결과를 하나하나 다시 확인해야 했다.

AI 결과를 사람이 매번 다시 확인해야 하면 QA를 맡긴 의미가 없다. 그래서 무엇을 보게 할지, 결과를 어떻게 믿을지, 찾은 걸 누가 고칠지를 하나씩 정하게 됐다.

## 페르소나마다 이탈 조건 정해두기

QA를 기능 목록으로 돌리면 버튼이 눌리는지는 확인할 수 있지만, 사용자가 어디서 무슨 이유로 이탈하는지 알 수 없다. 그래서 페르소나마다 목표와 불만, 그리고 이탈 조건을 적어두고 여정 스펙을 그 기준으로 짰다.

| 페르소나 | 목표 | 이탈 조건 |
| --- | --- | --- |
| 채원(27), 현직 UIUX 디자이너 | 취향에 맞는 작품을 폰으로 끝까지 읽고, 앱을 닫았다 열어도 이어서 보기 | 앱을 다시 열면 처음으로 돌아가 있음, 선택지를 눌러도 반응이 없어서 다시 눌렀더니 두 번 진행됨 |
| 민준(11), 보급형 폰을 쓰는 초등학생 | 형이 보내준 링크로 들어와서 기다리지 않고 바로 놀기 | 5초 넘게 반응 없는 로딩, 연타하고 뒤로가기를 누른 뒤 새로고침해도 복구되지 않음, 10초 안에 누를 곳이 안 보임 |
| 도현(22), 서비스 제한을 우회하는 꼼수를 찾는 사용자 | 꼼수를 찾아서 캡처로 자랑하기 | 이탈 조건 대신 꼼수가 통하는지를 본다. 남의 편집본에 들어가거나 재화를 두 번 받는 데 성공하면 그 자체가 치명 결함 |

이 밖에 친구끼리 역할놀이를 하려는 중학생, 선택지가 있는 소설을 링크를 아는 사람에게만 공개하려는 고등학생, 만든 퀘스트를 패키지로 팔려는 전직 게임 기획자까지 총 6명의 페르소나를 만들었다.

이탈 조건이 정해지면 스펙이 무엇을 확인할지도 같이 정해진다. 예를 들어 민준 여정은 성격 급한 초등학생이라는 설정을 부여하여 폰 세로 화면에서 지도 목적지 버튼을 4번 빠르게 누르고, 화면이 넘어가는 중에 뒤로가기를 누르고, 새로고침한 뒤 상태줄에 체력이 다시 뜨는지를 본다. 초등학생이 실제로 할 법한 행동을 그대로 스펙으로 옮긴 것이다.

단 이 QA는 새 문제를 찾는 탐색용이고 회귀를 막는 건 원래 있던 e2e 코드가 맡는다. AI의 자연어 판단은 같은 화면에서도 실행마다 결론이 달라질 수 있기 때문에 CI의 성공이나 실패 조건으로 쓰지 않는다.

## 근거 없이는 확정 판정을 못 내리게 막기

디자이너 채원 여정을 처음 돌렸을 때 AI는 전체 공개로 게시한 콘텐츠가 상세 화면엔 비공개라고 뜬다는 걸 가장 심각한 `blocking` 등급으로 올렸다. 그런데 내가 직접 확인해보니 게시가 끝난 뒤에는 화면이 멀쩡히 보였다.

AI에게 다시 재현해보라고 하자 게시 요청의 서버 응답을 직접 떠서 다시 대조했고, 여정 스펙이 게시된 콘텐츠가 아니라 편집 중인 원본을 열어보고 있었다는게 드러났다. 스펙은 게시된 콘텐츠를 보도록 고쳤다. 소설 콘텐츠의 입력창이 명령어를 요구해 장르에 안 맞는다는 발견도 있었는데, 소설에서도 명령어를 지원하는 게 원래 기획이라고 알려주자 철회됐다. 이 회차에서만 AI가 올린 발견 4건이 오탐이거나 기획 의도를 잘못 읽은 것이었다.

이후 채원 여정만 다시 돌린 파일럿 회차에서도 AI가 결함이라고 보고한 7건을 코드와 서버 응답으로 대조해보니 6건이 테스트 쪽 계측 결함이었다. 예를 들어 AI는 `Failed to fetch`가 세 번 연속 찍힌 걸 보고 서버에 공통 원인이 있다고 했다. 그런데 브라우저 밖에서 curl로 같은 요청을 보내보니 서버는 12번 모두 평균 30ms로 정상 응답하고 있었다. 원인은 테스트가 화면을 이동하면서 진행 중이던 요청을 스스로 끊은 것이었다.

버튼이 정말 반응하지 않을 때와 테스트가 엉뚱한 버튼을 잡아 클릭이 일어나지 않았을 때가 똑같이 timeout으로 찍히기도 했다. 조작 실패를 `.catch(() => false)`로 덮어버리는 코드 때문에 클릭이 실패했는데도 요소가 없다고 기록되는 경우도 있었다.

이런 일이 생길 때마다 반복되지 않게 하려고 AI 메모리에 내용을 남겨뒀지만 오탐은 계속 나왔다. 그래서 지침 대신 헬퍼와 타입으로 막기로 했다. 판정을 세 등급으로 나누고, 일감으로 올릴 수 있는 건 `확정` 등급뿐이라고 명시했다.

| 등급 | 뜻 | 일감으로 올릴 수 있나 |
| --- | --- | --- |
| 관찰 | 화면에서 본 것을 기록만 함 | 아니오 |
| 미확인 | 기대와 다르지만 아직 원인을 모름 | 아니오 |
| 확정 | 코드나 서버 응답으로 원인을 짚음 | 예 |

확정 판정은 `confirmed()`로만 만들 수 있는데, 이 함수는 근거를 필수 인자로 받는다. 근거를 빠뜨리면 타입 에러가 나니까 근거 칸을 비워둔 채로는 확정을 만들 수 없고, 최소한 근거를 적는 단계를 거치게 된다.

```ts
export type Grade = '관찰' | '미확인' | '확정';

export type Judgement = { grade: Grade; label: string; detail: string; evidence: string | null };

// 기대와 다르지만 아직 원인을 모르는 것. 일감으로 올리면 안 된다
export const unverified = (label: string, detail: string): Judgement => ({
    grade: '미확인',
    label,
    detail,
    evidence: null,
});

// 근거는 파일:라인이나 서버 응답 원문. 빠지면 확정을 못 만든다
export const confirmed = (label: string, detail: string, evidence: string): Judgement => ({
    grade: '확정',
    label,
    detail,
    evidence,
});
```

없다는 판정도 `expectAbsent()`로만 내게 했다. 채원 파일럿의 오탐 6건 중 4건이 로케이터 하나로 못 찾은 걸 화면에 없다고 판정한 경우였다. 같은 이름의 요소가 여러 개면 숨은 요소를 집을 수 있고, 라벨이 조금만 바뀌어도 못 찾는다. 그래서 로케이터를 2개 이상 받고 근거가 있을 때만 확정으로 올라가게 작업했다.

> Playwright는 `page.getByRole('button', { name: '편집' })`처럼 버튼인지 링크인지와 화면에 보이는 이름으로 요소를 찾는데, 이렇게 요소를 찾는 조건을 로케이터라고 한다.

```ts
export const expectAbsent = async (options: {
    label: string;
    locators: Locator[]; // 서로 다른 방식으로 같은 대상을 찾는 로케이터들
    timeout?: number;
    evidence?: string; // 서버 응답 원문이나 파일:라인
}): Promise<AbsenceResult> => {
    if (options.locators.length < 2) {
        throw new Error(/* ... */); // 하나만 보고 없다고 하지 않는다
    }
    // ...
    if (found.length > 0) {
        return { absent: false, judgement: observed(options.label, `있음 (${found.join(', ')}로 확인)`) };
    }
    const detail = `로케이터 ${options.locators.length}개 모두에서 못 찾음`;
    return {
        absent: true,
        judgement: options.evidence
            ? confirmed(options.label, detail, options.evidence)
            : unverified(options.label, `${detail} — 근거가 없어 발견으로 올릴 수 없다`), // 근거가 없으면 미확인에 머문다
    };
};
```

예를 들어 도현 여정에서 남의 콘텐츠 상세 화면에 편집 진입점이 없는지 볼 때는 버튼으로도 찾고 링크로도 찾는다. 둘 다 없을 때만 없다고 보고, 근거에는 이 편집본의 주인이 도현이 아니라는 사실과 서버 응답을 남긴다.

```ts
const editEntry = await expectAbsent({
    label: '[A2] 남의 콘텐츠 상세의 편집·삭제 진입점',
    locators: [
        page.getByRole('button', { name: /^\s*(수정|편집|삭제|에디터)/ }), // 버튼으로 찾기
        page.getByRole('link', { name: /^\s*(에디터|수정|편집)/ }), // 링크로 찾기
    ],
    evidence: /* ... */, // 이 편집본의 주인이 도현이 아니라는 사실과 서버 응답 원문
});
```

앞에서 본 민준 여정도 이 등급으로 짜여 있다. 연타한 뒤 화면이 어떻게 바뀌었는지는 `관찰`로 남기고, 새로고침 후 체력이 다시 안 뜨면 바로 결함으로 단정하지 않고 `미확인`으로 남긴다. 같은 증상이라도 어떤 상태에서 봤는지에 따라 판정이 달라질 수 있기 때문이다. 실제로도 체력이 빈칸으로 보이는 증상이 두번 탐지됐는데, 디자이너 채원 여정에서는 캐릭터 생성이 덜 끝난 상태의 정상 표시였고, 중학생 서연 여정에서는 첫 참여 때 캐릭터 생성 안내가 오지 않는 진짜 버그였다.

이렇게 등급 체계로 바꾼 직후 처음 돌린 회차에서는 오탐이 0건이었다. 야호~

## AI가 고칠 것과 사람이 정할 것을 나누자

결함을 찾은 다음엔 누가 고칠지가 남는다. AI가 찾은 걸 AI가 다 고치게 두면 빠르긴 하지만, 화면 흐름이나 문구처럼 정책이 걸린 결정까지 AI가 임의로 내리게 된다는 문제가 있었다.

그래서 두 조건을 둘 다 만족하는 결함만 AI가 직접 고치게 했다. 기획 의도에 명백히 어긋나야 하고, 고치는 방법이 하나뿐이어야 한다. 예를들면 오탈자나 조건이 반대로 들어간 경우, 잘못된 키나 빠진 가드 같은 것들이다. AI는 고친 뒤 `npm run verify`(lint, format, 타입, 테스트)까지 통과시키고, 커밋은 사람이 직접 한다. 명백한 결함이라도 어느 화면으로 보낼지, 어떤 문구로 바꿀지처럼 방법이 여럿이면 일감으로 넘긴다.

예를 들어 비공개 콘텐츠의 상세 화면에서 제작자 본인에게도 공유하기 메뉴가 안 보이는 버그가 있었는데 이는 대조 필드가 잘못되어 생긴 명확한 현상이었기 때문에 AI가 바로 고칠 수 있었다. 반대로 다른 계정의 편집본을 열고 고칠 수 있던 권한 누락 관련 버그는 백엔드 수정이 필요해서 일감으로 넘겼다. 또 AI가 임의로 정책을 정하게 되면 나중에 확인/수정하는 비용이 더 크기 때문에 애매하면 무조건 일감으로 (사람이 확인하도록) 넘기기로 정했다.

## 배운점

QA를 빨리 돌리는 건 지난 글에서처럼 e2e와 AI를 결합해서 해결했지만, 막상 팀에서 쓰려고 하니 AI가 올린 결과를 믿을 수 있게 만드는 일이 더 중요했던 것 같다. 등급 체계를 갖춘 뒤에는 꼼수를 찾는 도현 여정과 패키지를 파는 게임 기획자 여정에서 배포 전에 서버 쪽 결함을 여러 건 찾아 백엔드에 넘기기도 했다.

- 다른 계정의 편집본을 열고 고칠 수 있는 권한 누락
- 구매자가 판매자의 상품을 수정하거나 판매를 중단할 수 있는 문제
- 가격 검증이 빠져서 재화가 부당하게 늘어나는 문제
- 동시에 구매하면 두 번 정산되는 문제
...

결국 AI가 따라갈 시나리오는 기획 의도와 도메인 지식을 아는 사람이 정하고, AI의 판정은 메모리에 적어둔 지침 대신 헬퍼와 타입으로 강제한 게 팀에서 믿고 쓸 수 있는 QA를 만든 핵심인 것 같다.
