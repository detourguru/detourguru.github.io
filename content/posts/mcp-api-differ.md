요즘 MCP가 참 핫한데 나도 MCP를 제법 활용하고 있다. 예를들면 클로드한테 구글 캘린더 일정 추가하라고 하기, 트렐로에 카드 추가하라고 하기 등등. [Playwright MCP로 QA 속도를 개선한 글](https://detourguru.github.io/posts/mcp-qa-too-slow/)도 하나 썼다.

근데 그 글을 다시 읽어보니 MCP가 뭔지는 한 줄도 설명이 없다. `붙였더니 되더라, 근데 느리더라, 그래서 이렇게 고쳤다!` 남이 만들어둔걸 연결해서 시키기만 하면 되니까 그 밑에서 뭐가 오가는지는 볼 일이 없었던 것이다. 그냥 AI가 가져다 쓸 수 있는 API 정도로 이해하고 넘어갔었다.

그런데 마침 우리 서비스에도 MCP 서버가 붙었다. 클로드 커넥터로 연결해놓고 말을 걸면 우리 플랫폼에 알아서 콘텐츠가 추가된다. 자연어로 말을 걸어서 AI가 플랫폼 구조에 맞는 콘텐츠를 생성하게 하다니. 진짜 신기한데 대체 어떻게 된 구조지? 그래서 우리 백엔드가 만든 MCP 코드를 한번 보면서 MCP에 대해서 공부해보기로 했다.

## MCP는 LLM이 도구를 일관된 방식으로 사용할 수 있게 하는 프로토콜이다

제목이 좀 길었는데 아무튼 위 내용 그대로다. 처음에는 나도 저 문장을 보고도 이해가 잘 안갔다. 그러니까 결국 API를 어떻게 쓸지 알려주는 지침이라는건가?

MCP는 내부적으로 JSON-RPC 2.0을 사용한다. 즉 메시지는 method, params, id 형태로 오가지만, 중요한 건 전송 포맷이 아니라 모든 MCP 서버가 tools/list, tools/call 같은 공통 인터페이스를 제공한다는 점이다.

> JSON-RPC 2.0는 이름에서부터 알 수 있듯 JSON 기반의 가벼운 통신 규약인데, `{"jsonrpc": "2.0", "method": "...", "params": {}, "id": 1}` 이렇게 호출할 함수명인 method와 인자와 식별자를 실어 요청을 보낸다. 응답 없이 요청만 가는 notification과 요청의 batch 전송도 지원해준다.

MCP는 표준 메서드를 몇가지 지원하고 있는데 (REST의 HTTP 메소드를 떠올려보자), 흐름으로 보면 이렇다. 커넥터를 연결하면 `initialize`로 확인하고 `tools/list`로 이 서버가 뭘 할 수 있는지 목록을 받아온다. 그 다음부터 사용자가 뭘 시킬 때마다 `tools/call`로 그중 하나를 부르는 것이다. 

이 정도만 놓고 보면... 그냥 REST 규약이 아닐 뿐 API가 맞아 보인다. 그렇다면 API와의 차이는 대체 뭘까?

## 제약이 프롬프트에 있느냐 스키마에 있느냐

사실 MCP가 붙기 전부터도 우리 서비스엔 AI 생성 기능이 있었다. 사용자가 폼을 적고 제출하면 서버가 외부 LLM을 API 호출해서 콘텐츠를 만들어준다. 이 방식에서 무엇을 어떻게 만들지는 서버가 정한다. 정확히는 LLM을 호출할 때 같이 넘겨주는 시스템 프롬프트가 정한다. 실제 프롬프트는 못 옮기지만 이런 식이 될 것이다.

```
[항목 규칙]
- 첫 번째 항목은 반드시 A 타입이어야 한다.
- 10자 이상 150자 이하.
...

[배치 규칙]
- 반드시 정확히 N개를 생성한다.
- 첫 번째 슬롯의 좌표는 고정값이다.
- 문장 끝 온점 뒤에 개행 2회
...
```

사용자는 제목이나 설명 등 컨셉을 form으로 넘겨주고 LLM은 그 컨셉을 가지고 프롬프트를 읽은 다음 응답을 생성한다. 그러니까 사용자가 채우는 건 빈칸 몇 개뿐이고 뼈대는 서버가 미리 다 정해둔 셈이다.

그런데 MCP 서버에는 이런 프롬프트가 없다. 대화는 클로드 채팅 창에서 일어나고 MCP 서버는 그 대화를 자동으로 전달받진 않는다. 대신 `tools/list`를 부르면 어떤 툴이 있고 각 툴이 어떤 모양의 인자를 받는지를 JSON Schema로 돌려준다. 응답을 가져오는 제약이 API 방식은 서버 안의 자연어 프롬프트 내에 있고 MCP는 스키마에 있는 것이다.

이건 생각보다 더 큰 차이이다. AI를 사용해본 사람들은 다 알겠지만 아무리 프롬프트를 길고 상세하게 적어둔들 LLM이 한번 누락하면 그대로 끝이다. 지켰는지 안 지켰는지도 응답을 받아서 일일이 검사해봐야 안다. 반면 스키마로 제약을 둔다면 규격이 정해진것이 되기 때문에 LLM이 맞게 보내면 받고 아니면 거부할 수 있게된다.

다만 스키마가 전부를 커버하진 못한다. 스키마가 잡아주는 건 결과 데이터의 형태지 그 내용은 아니라서 `A 필드에 a 값 불가`와 같은 제약사항은 스키마 문법으로 표현할 방법이 없다. 그래서 우리 서버는 툴을 만들어놔서 자연어 프롬프트를 일정부분 더 사용해 LLM을 이해시키는데 사용하고 있었다.

스키마 방식은 어떤 툴이 어떤 인자로 호출될지를 다 정의해두지 않으면 다른 제약사항이 무의미해질 가능성이 있기 때문에 사용자가 뭘 요청할지 예측 가능한 범위 내에서만 설계가 가능하다. 반대로 프롬프트를 통한 제약은 자유도가 높아서 LLM이 알아서 보고 해석해서 응답을 내놓을 수가 있다. (물론 정확도는 보장할 수 없을 수 있다) 

우리는 이미 생성 규칙이 명확하게 잡혀있었기 때문에 스키마 방식이 더 유리했지만 만약 규칙이 계속 바뀌거나 범위가 넓은 기능에 대해서 스키마방식을 적용하려 했다면 유지보수 비용이 더 많이 들었을 것 같다.

## 그래서 언제 MCP를 붙이는 게 좋을까

우리 서비스에 동일한 기능이 API로도 MCP 방식으로도 있었기 때문에 비교를 좀 해볼 수 있었다.

만약 자연어로만 설명할 수 있는 계열이고 사용자의 맥락이 중요한 기능이라면 form은 사용할 수 없다. form은 정해진 항목대로 정해진 값을 받아서 사용할 수밖에 없기 때문이다. 하지만 MCP를 사용하려면 커넥터도 연결해야하고 AI 구독도 필요하기 때문에 진입 장벽이 다소 높다.

또 MCP는 사용자를 우리 화면으로 불러오는 대신 사용자가 사용하던 AI 환경에서 우리 기능을 사용할 수 있게 하는 것이므로 플랫폼 서비스에서 사용하기에는 다소 부적절할 수 있겠다는 인상도 받았다. 결국 플랫폼에 체류하며 콘텐츠를 이용하게 하는 것이 더 중요할 수도 있기 때문이다.


## 배운점

REST API 문서는 사람이 읽고 코드를 작성한다. 하지만 MCP는 LLM이 스키마와 규칙을 읽고 어떤 툴을 어떻게 호출할지 결정한다. 그러니까 사용자가 "구글 달력에 일정 추가해줘" 라고 말하면 LLM이 그 채팅과 스키마와 규칙을 같이 읽고 그중 구글 캘린더에 쓸 수 있는 툴을 골라서 호출하는 것이다.

MCP를 사용한다고 모든 것이 해결되는 것도 아니고 결국 어느 쪽의 편의성을 제공하는 것이 더 중요한지를 따져보는 것이 중요한 것 같다.

REST는 사람들끼리 이렇게 보내면 이렇게 응답이 갈거야~라는 약속이고 MCP는 LLM들이 규칙과 스키마를 통해 뭘 할수 있는지 알려주는 것에 가까운 것 같다. 그래서 MCP 서버를 만드는 일은 엔드포인트를 만드는 것보다 설명서를 쓰는 일에 가깝다는 생각이 들었다.

이제 남이 만든 MCP를 붙일 때도 좀 다르게 보일 것 같다. 전에는 붙였을때 되네 안 되네만 봤는데 지금은 어디까지 제약을 걸어놨을지 궁금해질 것 같다.
