회사에서 개발 중인 서비스인 몽글에서 AI로 콘텐츠를 만들면 생성 작업은 서버에서 백그라운드로 돈다. 생성이 다 끝나면 서버는 미리 열어둔 SSE 연결로 `createComplete` 이벤트를 보내준다. 그 전까지는 프로필 영역의 `내 방 꾸미기` 버튼에 로딩 스피너가 돌고, 누르면 "아직 만들고 있어요." 토스트만 뜬다. 브라우저가 이 이벤트를 받아야 버튼이 풀린다.

그런데 서버에서는 30초 만에 생성이 끝났는데도 새로고침하기 전까지 버튼이 계속 잠겨 있는 일이 생겼다. 그 뒤에는 iOS에서 친구 요청을 받아도 알림이 안 오고 친구 목록도 갱신되지 않는 문제가 있었다. 둘 다 서버가 먼저 보내주기로 한 이벤트가 화면까지 오지 않은 경우였다.

## 기능마다 서버와 주고받는 방식이 다르다

몽글에서 서버와 데이터를 주고받는 방식은 네 가지다. 누가 먼저 보내는지와 누구와 누구 사이인지로 나눠보면 기능마다 무엇을 골랐는지가 보인다.

| 방식 | 누가 먼저 보내나 | 누구와 누구 사이 | 몽글에서 쓰는 곳 |
| --- | --- | --- | --- |
| polling | 브라우저가 정해진 간격으로 다시 묻는다 | 브라우저와 서버 | 결제 결과 확인, 관리자 서버 상태 |
| SSE | 연결을 열어두면 그 뒤로는 서버만 보낸다 | 브라우저와 서버 | 친구 요청, 생성 완료, 운영 공지와 강제 로그아웃 |
| WebSocket | 연결을 열고 나면 양쪽 다 보낸다 | 브라우저와 서버 | 게임 플레이, DM 대화방 |
| 웹훅 | 일이 생긴 서버가 상대 서버로 보낸다 | 서버와 서버 | 결제사가 결제 결과를 우리 서버로 |

게임 플레이에서는 플레이어가 둘러보기(`lookAround`), 전투 시작(`startBattle`), 거래 수락 같은 명령을 계속 보낸다. 그 결과도 같은 연결로 바로 받아야 해서 WebSocket을 쓴다. 반대로 친구 요청이나 생성 완료는 언제 생길지 서버만 알고 브라우저가 보낼 건 없다. 게다가 게임 WebSocket은 플레이 화면에 들어가야 그 게임으로 연결되고 나오면 끊긴다. 그런데 이런 이벤트는 플레이 화면 밖에서도 받아야 한다. 그래서 로그인하면 브라우저가 `/sse/connect`에 요청을 하나 보내고 그 HTTP 응답을 끊지 않은 채 [SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) 이벤트를 계속 받는다. 이 연결은 앱 전체에서 하나만 열어두고 화면을 옮겨도 다시 연결하지 않는다. (이 연결이 두 번 열리던 문제는 [예전 글](/posts/faced-three-race-conditions/)에서 다뤘다.)

polling은 바뀐 게 없어도 정해진 간격마다 요청이 나간다. 새 콘텐츠 만들기 창에서 이미지 생성을 기다리는 단계는 원래 1.5초마다 완료 여부를 묻는 polling이었다가 SSE 구독으로 바뀌었다. 반면 관리자 서버 상태 화면에 띄우는 프로세스별 수치와 작업 큐는 서버에서 각각 10초와 15초 주기로 갱신되는 값이다. SSE로 받아도 더 빨라지지 않으니 이 화면은 SSE를 쓰지 않고 10초 polling으로 만들었다.

## 웹훅은 서버가 받고 결제 결과 화면은 다시 묻는다

웹 결제는 결제창에서 결제가 끝나면 두 가지 일이 따로 일어난다. 결제사가 우리 서버로 결과를 보내고(웹훅), 결제창은 브라우저를 결제 결과 화면으로 돌려보낸다. 이 중 결과 화면으로 돌아오는 건 브라우저 이동이라 중간에 빠지거나 위조될 수 있다. 그래서 백엔드에서는 이때 화면만 넘기고, 몽글 재화인 각설탕은 웹훅과 서버의 주기 작업에서만 지급한다. 웹훅이 늦거나 안 오면 이 주기 작업이 5분마다 대기 중인 주문의 거래 상태를 결제사에 직접 물어서 지급한다. 서버끼리도 상대가 보내주길 기다리다가 안 오면 다시 묻는 구조다.

지급이 끝났는지 확인하려고 결제 결과 화면에서는 서버에 주문 상태를 2.5초마다 다시 묻게 작업했다.

```tsx
const POLL_INTERVAL_MS = 2500;
const PENDING_TIMEOUT_MS = 60 * 1000;
...
    // 지급 여부가 아직 안 정해졌고 1분이 안 지났으면 2.5초 뒤 다시 묻는다
    refetchInterval: (query) => (!timedOut && isUnsettled(query.state.data) ? POLL_INTERVAL_MS : false),
```

React Query의 [`refetchInterval`](https://tanstack.com/query/v5/docs/framework/react/reference/useQuery)에 함수를 넘기면 쿼리 상태를 보고 다음 조회 여부를 정할 수 있다. 여기서 `isUnsettled`는 응답이 아직 없거나 요청이 실패했거나 주문 상태가 `pending`이면 지급 여부를 아직 모르는 것으로 본다. 끝난 것으로 보는 건 완료나 실패처럼 주문 상태가 정해졌거나 서버가 거절 메시지를 줬을 때뿐이다. 그래서 요청이 한 번 실패해도 결제 실패로 띄우지 않고 2.5초 뒤에 다시 묻는다. 1분이 지나면 `timedOut`이 켜져서 더는 묻지 않는다. 대신 잠시 후 보유 각설탕을 다시 확인해 달라고 안내한다. 그 뒤의 지급은 서버의 5분 주기 작업이 맡는다.

## SSE 이벤트가 연결이 없는 프로세스로 갔다

`내 방 꾸미기` 버튼이 풀리지 않던 원인은 서버 구조에 있었다. API 서버는 pm2 클러스터 모드라서 같은 서버 프로세스 4개가 요청을 나눠 받는다. 그리고 SSE 연결 목록은 각 프로세스가 자기 메모리에만 들고 있다. 그런데 생성 완료 이벤트는 생성 작업을 처리한 프로세스가 보낸다.

예를 들어 내 SSE 연결은 1번 프로세스가 들고 있는데 생성 작업은 3번 프로세스에서 끝났다고 해보자. 3번 프로세스의 연결 목록에는 내 연결이 없다. 그래서 완료 이벤트는 3번 프로세스의 대기 큐에 남고 나한테는 오지 않는다. 진단해보니 7번 중 4번이 이렇게 전달되지 않았다. 이벤트를 만든 프로세스와 연결을 들고 있는 프로세스가 다를 수 있다는 것이 문제였다.

<!-- 그림: 프로세스 4개 중 1번이 내 SSE 연결을 들고 있고, 생성 작업은 3번에서 끝나 완료 이벤트가 3번 대기 큐에 남는 흐름 -->

프로세스끼리 이벤트를 넘겨주는 건 백엔드에서 고쳐야 했다. 그 전까지 SSE를 못 받아도 버튼이 풀리도록 프론트에서는 생성 중일 때만 10초마다 사용자 정보와 내 콘텐츠 목록을 다시 받게 했다.

```ts
export const GAME_CREATION_POLL_MS = 10_000;

export const useGameCreationFallbackPoll = (isGameCreating: boolean): void => {
    const queryClient = useContext(QueryClientContext);

    useEffect(() => {
        if (!isGameCreating || !queryClient) return; // 생성 중일 때만 돈다

        const timer = setInterval(() => {
            void queryClient.invalidateQueries({ queryKey: ['CURRENT_USER'] });
            void queryClient.invalidateQueries({ queryKey: ['MY_GAMES'] });
        }, GAME_CREATION_POLL_MS);

        return () => clearInterval(timer); // 생성이 끝나 false가 되면 멈춘다
    }, [isGameCreating, queryClient]);
};
```

SSE가 제때 오면 캐시에 있는 `createComplete` 값이 바로 `true`로 바뀐다. 그러면 생성 중인지를 나타내는 `isGameCreating`이 `false`가 되면서 polling도 같이 멈춘다. SSE를 놓쳐도 다음 조회에서 받은 목록으로 이 값이 `true`로 바뀌기 때문에 늦어도 10초 남짓 뒤에는 버튼이 풀린다. 테스트로는 생성 중일 때만 10초마다 두 쿼리를 다시 받고, 생성이 끝나거나 화면을 벗어나면 멈추는지를 확인했다.

새 콘텐츠 만들기 창에서 이미지 생성을 기다리는 단계도 같은 이유로 늦어졌다. 이 단계는 이미지 생성이 끝났다는 SSE `stepImagesReady`를 기다렸다가 다음 화면으로 넘어간다. 그래서 이 이벤트를 놓치면 이미지가 다 만들어졌는데도 최대 대기 시간인 60초를 다 채우고서야 넘어갔다. 여기는 SSE 구독을 그대로 두고 3초마다 남은 이미지 수를 묻는 polling을 보조로 같이 돌렸다. SSE와 polling 중 먼저 완료를 알려주는 쪽에서 다음 화면으로 넘어가게 작업했다. 보조 수단이라 간격은 예전에 polling만 쓸 때의 1.5초보다 느슨하게 잡았다.

```ts
export const IMAGES_POLL_MS = 3000;
...
await new Promise<void>((resolve) => {
    let settle: () => void = () => {};
    const timeoutId = setTimeout(() => settle(), IMAGES_WAIT_MAX_MS); // 60초가 지나면 그냥 넘어간다
    const unsubscribe = subscribeStepImagesReady((readyGameId) => {
        if (readyGameId !== gameId) return;
        settle(); // SSE가 먼저 오거나
    });
    const pollId = setInterval(() => {
        void stepApi.imagesStatus({ gameId }).then((res) => {
            const { payload } = readStepResult<AiStepImagesStatusResult>(res);
            if (payload?.pending === 0) settle(); // 조회에서 남은 이미지가 0개면
        });
    }, IMAGES_POLL_MS);
    let settled = false;
    settle = () => {
        if (settled) return; // 셋 중 먼저 온 것만 처리한다
        settled = true;
        clearTimeout(timeoutId);
        clearInterval(pollId);
        unsubscribe();
        resolve();
    };
});
```

SSE와 조회 응답, 타임아웃이 거의 동시에 올 수 있어서 `settled`로 타이머와 구독을 한 번만 정리한다. 테스트로는 SSE가 안 와도 조회가 `pending: 0`을 돌려주면 60초를 기다리지 않고 넘어가는지 확인했다. 아직 남은 이미지가 있을 때 계속 기다리는지도 같이 봤다.

이후 백엔드에서 프로세스끼리 이벤트를 넘겨주는 수정이 들어갔다. 이벤트를 보내는 프로세스는 자기가 들고 있는 연결에 바로 쓰는 것과 별개로 DB의 `sse_events` 컬렉션에도 적어둔다. 그리고 각 프로세스는 1초 주기로 이 컬렉션을 읽어서 자기가 들고 있는 연결에 전달한다. 앞의 예라면 3번 프로세스가 적어둔 완료 이벤트를 1번 프로세스가 읽어서 내 연결로 보내주는 식이다. 브라우저에 SSE를 제대로 보내려고 서버 안에서는 polling을 하게 된 셈이다.

## 끊긴 SSE 연결이 살아 있는 것처럼 남았다

iOS에서 친구 요청 알림이 안 오던 문제는 원인이 달랐다. 기존 재연결 로직은 연결이 닫히거나 에러가 났다는 `onclose`나 `onerror`가 와야 돌았다. 그런데 끊긴 SSE 연결이 에러도 종료도 없이 멈춘 채로 남아서 둘 다 오지 않았던 것이다. 게다가 서버는 친구 요청과 수락 이벤트를 그 순간 붙어 있는 연결에만 보내고 큐에 남기지 않는다. 그러니 나중에 다시 연결돼도 놓친 이벤트는 다시 오지 않는다.

그래서 백엔드 SSE 라우트에 주석 처리돼 있던 heartbeat를 살려서, 서버가 연결이 살아 있다는 신호로 25초마다 `ping` 이벤트를 보내게 했다. 프론트는 ping이 오기 시작한 연결에서 60초 동안(ping 두 번) 아무것도 못 받으면 그 연결을 버리고 새로 연다. 앱에 돌아왔을 때도 마지막으로 받은 지 30초가 넘었으면 바로 새로 연다. 마지막 ping을 받고 20초 만에 돌아오면 연결을 그대로 두고, 2분 뒤에 돌아오면 바로 새로 여는 식이다.

이렇게 새로 연 연결에서는 친구 목록과 생성 상태를 다시 받아서 끊겨 있던 동안 놓친 이벤트를 메운다. 그러니까 토스트는 놓치더라도 목록은 맞출 수 있다.

게임 플레이 WebSocket은 이보다 먼저, 앱에 돌아오면 `ping`을 보내고 3초 안에 `pong`이 없으면 화면을 새로고침하게 되어 있었다.

## SSE 이벤트마다 놓쳤을 때 메우는 방법이 다르다

운영 공지나 출금 계좌 변경 같은 알림은 DB에 먼저 저장한 뒤 SSE를 보낸다. 운영 공지 SSE는 접속 중인 사람에게만 온다. 못 받은 사람도 알림함과 배지로 보게 되어 있어서 따로 메우지 않는다. SSE를 받았을 때도 배지 숫자를 화면에서 1씩 더하지는 않는다. 배지는 서버가 세어 보낸 안 읽은 수로 바꾸고 알림 목록은 다시 받게 작업했다.

출금 계좌 알림은 계좌 정보를 바꾸고 변경 이력을 남기는 트랜잭션 안에서 함께 저장된다. 그런데 트랜잭션은 다른 요청과 충돌하면 처음부터 다시 실행될 수 있다. 그러면 앞선 시도에서 만든 알림은 롤백된다. 그 시도 안에서 SSE를 보냈다면 DB에 없는 알림을 이미 알린 셈이 되기 때문에 백엔드에서는 이 SSE를 커밋이 끝난 뒤에 보낸다.

친구 요청은 다시 연결될 때 목록만 다시 받는다. polling까지 같이 돌리는 건 생성 완료나 이미지 생성 완료, 운영자 화면의 전체 공지 발송 완료처럼 놓치면 화면이 진행 중 상태에서 멈춰 버리는 이벤트다.

이런 polling은 전부 진행 중 상태인 동안만 돌고 상태가 바뀌면 멈춘다. 공지 발송도 보내는 중인 공지가 있는 동안만 3초마다 목록을 다시 받는다. DM 목록은 조건이 조금 다르다. 앱 전체에서 하나만 열어두는 SSE 연결이 붙어 있으면 polling을 끄고, 끊겨 있을 때만 5초마다 다시 묻는다.

## 배운점

몽글에서 실시간 연결이 놓친 걸 메운 방법을 모아보면 전부 다시 묻는 방식이었다. 브라우저는 서버에, 서버는 결제사와 DB에 다시 묻는다. 결국 SSE나 웹훅은 빨리 알려주는 역할이고, 끝났는지를 확정하는 건 다시 묻는 쪽이 맡아야 하는 것 같다.
