회전문에서는 공연 캐스팅보드 이미지를 올리면 AI가 표를 읽어서 회차마다 누가 나오는지 캘린더에 채워준다. 처음에는 AI가 읽은 회차를 확인 없이 바로 저장했다. 근데 AI가 읽은 값은 틀릴 수 있고 한 번 저장하면 다른 사람에게도 그대로 보인다. 그래서 저장하기 전에 업로더가 직접 확인하는 바텀시트를 붙였다. ([#14 확인 바텀시트](https://github.com/detourguru/hoejeonmun/issues/14))

그런데 이번엔 확인할 게 너무 많았다. 캐스팅보드는 이미지 한 장에 회차가 많으면 200행까지 들어가는데, 확인 화면은 이걸 전부 날짜와 배우 입력칸이 달린 카드로 늘어놓고 모든 회차를 저장 대상으로 체크해둔 상태였다. 이러면 스크롤만 내리다가 그대로 저장을 누르기 쉽다.

## 분석이 끝나면 회차마다 확신도가 붙어 온다

이미지를 올리고 분석이 끝나면 회차마다 날짜, 시간, 배역과 배우에 더해 확인이 필요한지 가를 값 세 개가 같이 온다.

```ts
export type ParsedPerformance = {
  date: string;
  weekday: string;
  time: string;
  casting: Record<string, string[]>; // 배역명 -> 배우명 목록
  ...
  imageIndex: number; // 몇 번째 이미지에서 읽었나
  confidence: number; // AI가 회차마다 매긴 확신도 (0~1)
  castMismatch?: boolean; // KOPIS 출연진과 겹치는 배우가 없음
  unsureRoles?: string[]; // 여러 번 읽었더니 결과가 갈린 배역
};
```

확신도가 0.7 이하인 회차가 하나라도 있으면 서버가 같은 이미지를 두 번 더 읽어서 다수결로 배역을 정한다. 이때 결과가 갈린 배역은 값을 채우지 않고 이름만 `unsureRoles`에 담는다. `castMismatch`는 읽어온 배우 이름을 KOPIS(공연예술통합전산망)에 등록된 출연진과 대조해서 붙인다.

확인 화면에는 원본 이미지 썸네일을 같이 두고, 누르면 원본 크기로도 볼 수 있게 했다. 저장 버튼 위에는 `AI가 이미지에서 읽어낸 값이라 틀릴 수 있어요. 저장하면 다른 사람에게 그대로 보여요.`라는 안내를 둬서 왜 확인해야 하는지도 같이 알려준다.

## 첫 번째: 200행이 전부 입력칸으로 펼쳐진다

회차마다 카드 모양이 똑같다 보니 어떤 회차를 먼저 봐야 하는지 화면이 알려주지 않았던 것이 문제였다. 그래서 AI에게 회차마다 확신도를 같이 받기로 했고, 확인이 필요한 회차만 카드로 펼치게 작업했다. ([#31 확인이 필요한 회차만 펼치기](https://github.com/detourguru/hoejeonmun/issues/31))

날짜와 시간순으로 정렬한 회차 `ordered`를 확인이 필요한 회차와 아닌 회차로 나눈다.

```tsx
const CONFIDENCE_THRESHOLD = 0.7;

...

const needsReview = (performance: ParsedPerformance) =>
  performance.confidence < CONFIDENCE_THRESHOLD || // 확신도가 낮거나
  performance.castMismatch || // KOPIS 출연진과 안 겹치거나
  (performance.unsureRoles?.length ?? 0) > 0; // 결과가 갈린 배역이 있으면

const lowConf = ordered.filter((order) =>
  needsReview(order.draft.performance),
);
const highConf = ordered.filter(
  (order) => !needsReview(order.draft.performance),
);
```

`lowConf`는 처음부터 카드로 그리고, `highConf`는 `{highConf.length}건 자동확정` 버튼 하나로 접어뒀다가 누르면 같은 카드로 펼친다.

예를 들어 확인 화면에 회차 세 개가 왔다고 해보자. 9/28 19:30 회차는 확신도가 0.95이고 9/29 14:00 회차는 0.6이다. 9/29 19:30 회차는 확신도가 0.9인데 `주인공` 배역이 다수결에서 갈렸다. 그러면 9/29의 두 회차만 카드로 펼쳐지고 9/28 회차는 `1건 자동확정` 버튼 안에 접힌다.

다만 확신도는 AI가 스스로 매긴 값이지 실제로 맞을 확률이 아니다. 확신은 높은데 틀린 회차가 접힌 채로 넘어갈 수 있어서 확인 화면에서는 확신도를 어떤 카드를 먼저 펼칠지 정하는 데만 쓴다. 접힌 회차도 `include: true` 그대로 저장 대상에 남고, 펼치면 고치거나 체크를 풀어 뺄 수 있다.

아 그리고 목록 위에 배역과 배우 이름만 모아둔 칸에서 고치면 접힌 회차까지 한 번에 반영된다. AI가 같은 배역을 `햄릿`과 `햄 릿`으로 나눠 읽었다면 `햄 릿`을 `햄릿`으로 한 번만 고치면 두 배우가 한 배역으로 합쳐진다.

## 두 번째: 맞는 캐스팅보드도 다른 공연 것으로 막힌다

업로더가 다른 공연의 캐스팅보드를 섞어 올릴 수도 있어서, 읽어온 배우 이름 중에 KOPIS 출연진과 겹치는 이름이 하나도 없으면 다른 공연 것으로 판단한다.

공연이 맞는지 보는 검증은 처음엔 이미지 묶음에서 하나만 맞아도 전체를 통과시켜서 A 공연에 섞어 올린 B, C 공연 이벤트까지 등록되기도 했다. ([#11 공연 일치 검증](https://github.com/detourguru/hoejeonmun/issues/11)) 그래서 이미지마다 대조해서 하나라도 안 맞으면 요청 전체를 거부하게 바꿨다. 이번엔 맞는 이미지까지 같이 튕겨서 안 맞는 이미지의 회차만 빼도록 [다시 고쳤다](https://github.com/detourguru/hoejeonmun/commit/297d773).

그런데 빼는 것도 문제였다. KOPIS 출연진은 개막 시점의 명단이라 실제로 맞는 캐스팅보드도 이 대조에 걸릴 수 있다. 몇 년째 하는 오픈런 공연은 지금 캐스팅과 하나도 안 겹칠 수 있어서 이미 대조를 건너뛰고 있었다. 그래서 출연진 대조에 걸린 회차는 빼지 않고 표시만 해서 확인 화면까지 [보내게 바꿨다](https://github.com/detourguru/hoejeonmun/commit/ae45aa1).

```ts
const mismatchedImages = findCastMismatchImageIndexes(valid, show); // 겹치는 배우가 하나도 없는 이미지 번호들

const matched = valid.map((performance) =>
  mismatchedImages.has(performance.imageIndex)
    ? { ...performance, castMismatch: true } // 빼지 않고 표시만 한다
    : performance,
);
```

표시가 붙은 회차는 앞의 `needsReview`에 걸려 카드로 펼쳐지고, 카드 위에 `이 공연 캐스팅과 겹치는 배우가 없어요. 원본과 대조해 확인해주세요.`라는 빨간 경고가 뜬다. 이 동작은 `KOPIS 출연진과 겹치지 않는 이미지의 회차는 빼지 않고 castMismatch로 표시한다`라는 테스트로 고정해뒀다.

### 뺄지 물어볼지 검사마다 나누기

지금은 어떤 검사에 걸렸는지에 따라 처리가 다르다.

| 걸린 검사 | 처리 | 업로더가 보는 곳 |
| --- | --- | --- |
| 회차의 날짜와 시간 형식, 공연 기간, 요일, 빈 캐스팅, 중복, 이미지 번호 | 회차에서 뺀다 | 저장 결과의 제외 목록 |
| KOPIS 출연진과 겹치는 배우가 없음 | 빼지 않고 경고 | 펼쳐진 회차 카드 |
| 이벤트에 적힌 요일과 날짜가 안 맞음 | 빼지 않고 확인 요청 | 이벤트 카드 |
| 확신도 0.7 미만, 결과가 갈린 배역 | 빼지 않고 먼저 펼침 | 펼쳐진 회차 카드 |

빼지 않는 검사는 모두 검사 쪽이 틀릴 수 있는 경우다. 출연진 대조는 기준 명단이 낡을 수 있고 확신도는 AI가 스스로 매긴 값이다. 이벤트 요일은 원본 공지에 오탈자가 있을 수 있다.

이벤트 요일 대조도 처음엔 안 맞으면 버렸다. 그런데 `프리쇼 위크` 공지 중에 9월 1일(화)부터 9월 6일(월)까지로 읽힌 것이 있었다. 2026년 9월 6일은 일요일이다. 요일이 안 맞으면 버리던 코드에서는 이런 이벤트가 통째로 사라진다. 그래서 이벤트는 요일이 안 맞아도 버리지 않고 `이미지에 적힌 요일과 날짜가 맞지 않아요. 연도가 다를 수 있으니 원본과 대조해 확인해주세요.`라는 확인 요청을 붙여 [보내게 바꿨다](https://github.com/detourguru/hoejeonmun/commit/9a80068).

## 세 번째: 저장하고 나면 회차가 빠져 있다

제외 목록이 생기기 전에는 저장 결과에 `읽지 못한 행 N개는 건너뛰었어요.` 한 줄만 나왔다. 실제 제보에서는 저장은 됐는데 24일 회차가 빠져 있었고, 어떤 행이 왜 빠졌는지 알 수 없다 보니 저장 전체가 실패한 것으로 받아들여졌다. ([#9 실패 행 상세 노출](https://github.com/detourguru/hoejeonmun/issues/9))

이후로는 뺀 행마다 몇 번째 이미지에서 읽었는지와 AI가 읽은 원본 값, 빠진 사유를 같이 남긴다. 사유는 검사 규칙 하나에 문구 하나씩 맞췄다.

```ts
export const PERFORMANCE_SKIP_MESSAGE: Record<PerformanceSkipReason, string> = {
  invalid_date: "날짜 형식을 읽지 못했어요.",
  invalid_time: "시간 형식을 읽지 못했어요.",
  out_of_range: "공연 기간 밖의 날짜예요.",
  weekday_mismatch: "이미지에 적힌 요일과 날짜가 맞지 않아요.",
  ... // 빈 캐스팅, 중복까지 사유 7개
  invalid_image_index: "이미지 번호를 확인하지 못했어요.",
};
```

`Record<PerformanceSkipReason, string>`으로 선언해서 사유가 하나 늘었는데 문구를 안 채우면 타입 에러가 난다. 저장 결과에는 `3개 행은 확인하지 못해 제외했어요.`가 나오고 `보기`를 누르면 행마다 어느 회차가 왜 빠졌는지 펼쳐진다. 일부만 빠진 저장은 실패가 아니니까 오류 색 대신 흐린 글씨로 둔다.

<!-- 그림: 저장 결과의 "3개 행은 확인하지 못해 제외했어요. 보기"와 펼친 제외 행 목록 -->

그런데 이 목록만 봐서는 알 수 없게 정상 행이 빠지는 경로가 두 개 더 있었다. ([#55 행 유실](https://github.com/detourguru/hoejeonmun/issues/55))

첫 번째는 AI가 요일을 빈 값으로 준 경우다. 회차의 요일 검사는 날짜로 계산한 요일과 AI가 읽은 요일을 그대로 비교하고 있었다. `2026-09-28`에 요일이 빈 값으로 오면 계산한 `월`과 같을 수가 없으니 날짜가 맞아도 `weekday_mismatch`로 빠졌다. 이벤트 쪽은 적힌 요일이 없으면 대조를 건너뛰는데 회차 쪽만 반대로 되어 있었던 것이 문제였다. 그래서 회차도 같은 함수로 [대조하게 고쳤고](https://github.com/detourguru/hoejeonmun/commit/1ea7ceb) 테스트로도 남겨뒀다.

```ts
export const agreesWithPrintedWeekday = (isoDate: string, printed: string) =>
  printed.length === 0 || getWeekday(isoDate) === toKoreanWeekday(printed); // 요일이 비어 있으면 대조하지 않는다
```

두 번째는 이어 붙인 이미지였다. 폭이 비슷하고 세로로 긴 캡처를 두 장 이상 올리면 서버가 이걸 위아래로 이어 붙인 이미지를 한 장 더 만든다. 이 이미지도 AI에게 같이 보낸다. 그러니까 이미지 2장을 올리면 AI는 0번과 1번 원본에 2번 이어 붙인 이미지까지 3장을 받는다.

문제는 AI가 어떤 행의 이미지 번호를 2번으로 적었을 때였다. 검증은 AI에게 보낸 이미지 수(3장)를 기준으로 해서 2번을 통과시켰다. 근데 저장할 때는 실제로 올린 0번과 1번 이미지만 있으니 그 행의 배우 배정이 통째로 빠졌다. 확인 화면에서는 멀쩡히 보였던 회차가 제외 목록에도 없이 배우만 사라진 것이다.

행 유실 이슈에는 2번을 원본 이미지 번호로 다시 연결하는 방법도 후보로 적어뒀다. 지금 코드는 검증 기준을 실제로 올린 이미지 수로 바꿔서 이런 행을 `이미지 번호를 확인하지 못했어요.`라는 사유로 제외 목록에 보낸다.

```ts
const realImageCount = images.length; // 이어 붙인 이미지를 뺀, 실제로 올린 이미지 수

const { performances, skipped } = normalizePerformances(
  parsed.performances,
  show,
  realImageCount, // 2장을 올렸으면 2번부터 invalid_image_index로 걸린다
);
```

최근 파싱 실패 기록 50건 중 6건은 AI가 이벤트나 캐스팅 변경 안내를 읽어왔는데 코드 검사에서 전부 걸러진 경우였다. 그중 4건은 앞의 프리쇼 위크 공지라 지금은 확인 요청으로 넘어온다. 근데 이렇게 전부 걸러지면 AI는 뭔가를 읽었는데 업로더에게는 표를 찾지 못했다는 안내가 나간다. 이 경우는 [#129 전부 걸러진 결과의 안내](https://github.com/detourguru/hoejeonmun/issues/129) 이슈로 따로 올려뒀다.

## 배운점

확인 화면을 붙일 때 문제로 본 건 AI가 틀린 값을 업로더가 못 보고 저장하는 것이었다. 그런데 그 뒤에 고친 것들을 보면 출연진 대조와 요일 대조가 맞는 값까지 막거나, 코드 때문에 정상 행이 빠지던 경우가 여럿이었다.

결국 AI가 틀릴 수 있다는 전제는 AI뿐 아니라 AI를 거르는 규칙과 그 규칙이 참고하는 데이터도 틀릴 수 있다고 보는 것까지 포함해야 하는 것 같다.
